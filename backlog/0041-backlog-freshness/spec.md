# backlog に実測の定位置を作る

backlog 候補の「現存確認（実測）の日時と結果」に定位置がなく背景の散文に埋まるため、リファインメント時に再測定の要否が判断しづらい。定位置を決める。

## 種別

改善

## 対象

- 場所: 候補は 2 つ。(a) backlog spec の「背景」冒頭に置く定型行の書式を CLAUDE.md「仕様」節で定める（凍結対象ではない）。(b) `task/TEMPLATE-spec.md` に欄を足す（**凍結対象**。見出しを増やすことになり影響が大きい）
- 公開面: なし（起草・リファインメントの規約）

## 背景

この項目は backlog。着手しない。progress は作らない。完了条件は未確定。

2026-08-22 のリファインメントでは、昇格判断の前に各候補の前提（対象コードが今もその形か）を人手で再実測し、その結果を依頼文に添えて spec-author へ渡した。実測の日時・手順・出力は spec の背景に散文で混ざるため、次のリファインメントで「いつ時点の観測か」「再測定が要るか」を拾い直すコストが毎回かかる。最終実測日と要点の定位置が 1 行あれば、鮮度の判断が機械的になる。

2026-08-23 のリファインメントで現存を確認した（実測行の定型は未導入のまま。この spec 群の
追記も従来どおり背景の散文で行っており、必要性は変わらない）。

## 仕様

変更後に満たしたい振る舞い（検証可能な命題に落とすのは昇格時）。

- backlog spec の「背景」に、定型の実測行を置く規約を決める。書式の候補: `実測: YYYY-MM-DD — <確認した事実の 1 行>`
- リファインメントで再実測したら、この行を更新する（履歴は git が持つ）
- 見出しは増やさない（テンプレートの見出し名・順番は変えない、の現行規約を守る）

## 範囲外

- 実測の自動化（コードの現存確認をツールで行うこと）
- 既存 backlog 全件への遡及適用（新規・更新分から適用でよい）

## 失敗時

なし（起草規約であり、実行時の失敗分岐はない）。

## 完了条件

未確定（incomplete）。昇格時に埋める。

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。

4. 「範囲外」を実装していない。
