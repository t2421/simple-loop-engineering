この項目は backlog。着手しない。progress は作らない。完了条件は未確定。

## 仕様

昇格時に確定する。以下は材料であり、断定ではない。

- 「例」表のコマンドはリポジトリルートから実行する
- 期待結果との照合は、少なくとも終了コード 0 と、`grep -c` 型の stdout 完全一致を扱う
- incomplete な backlog spec（「例」が未確定、「`<昇格時に記入>`」のまま）は、この検査の必須対象にしない。置いただけで落とさない
- **期待値を書き換えて検査を通さない。** 例の期待結果は完了条件の一部であり、通すために変えるのは検証を弱める
- アーカイブ / Status `Done` をこの検査の失敗で止めるかは、昇格時に決める（`archive.mjs` へ配線するか、`ci` だけにするか）
- 評価役は実装者から分離する（親が貼った出力の再実行ではなく、表のコマンドそのものを回す）

## 範囲外

- 人間のマージを機械で置き換えること
- Verify (外部) のレビュアーがサンドボックス内で `npm test` / `npm run ci` を再実行すること（0036 の対処を戻さない）
- アーカイブ済みの 0052 の spec・期待値を書き換えること（凍結対象。読むだけ。検査の最初の対象候補にはしてよい）
- 「例」が手順文だけでコマンドになっていない spec を、この作業で全部コマンド化すること

## 失敗時

未確定（incomplete）。昇格時に埋める。候補:

- コマンドが非 0、または stdout が期待と違う: 終了コード非 0。どの行がどう違ったかを出す。期待値は書き換えない
- 対象 spec の「例」が未確定（backlog の incomplete）: 必須にせず通す（または対象外と明示して終了コード 0）
- 対象の作業ディレクトリが無い: 黙って通さず、パスと理由を出して終了コード非 0
- 期待結果の解釈ができない（手順文だけ、など）: 推測して合否を付けない。理由を出して終了コード非 0。incomplete 扱いとするかは昇格時に決める
