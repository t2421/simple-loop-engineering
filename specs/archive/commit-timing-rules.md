# spec / progress のコミット・マージ規約

spec と progress をいつコミットし、いつ main へマージするかを CLAUDE.md にルール化する。

## 種別

改善

## 対象

- 場所: `CLAUDE.md`（「開発ループ」「進捗」「アーカイブ」の各節への追記、または独立した節の追加）
- 公開面: なし（エージェント向けドキュメント）

## 背景

現行フローでは spec / progress が実装と同じ PR でしか main に入らないため、次の問題がある。

- 未着手のバックログが main 上に存在せず、「作業を始める前に `progress/` を読む」が main では機能しない。worktree 並列（`specs/parallel-worktrees.md`）では破綻する
- 会話中に生まれた spec が進行中の作業ブランチに混入する（calc-page 作業中に別件 6 spec を同ブランチ上へ作成した実例）
- 実装 PR に spec の新規追加・変更が同居し、完了条件が実装に合わせて書かれても検知できない（`specs/guard-protected-paths.md` のガードが単純化できない）
- アーカイブのコミット先（main 直接か PR か）が未定義
- ルール変更（CLAUDE.md）が作業ブランチに混入する実例があった（calc-page 試行ログ 05:13）

## 仕様

CLAUDE.md に次の規約を追記する。

| 対象 | コミットのタイミング | マージ先・方法 |
|---|---|---|
| spec + progress の新規作成（Not Started） | 作成したらすぐ。`docs: add <作業名> spec/progress` | main から切った計画用ブランチ → 軽量 PR で main へ。実装 PR に混ぜない。レビューサブエージェントは不要、人間がマージする |
| progress の更新（チェック・試行ログ・PR URL） | 工程を進めるたび | 作業ブランチ。実装と同じ PR に含める |
| spec の変更 | 着手後は原則変更しない。必要なら変更内容と理由を試行ログに記録し、人間承認を経る | — |
| アーカイブ（Status Done・`archive/` への移動） | 実装 PR のマージ直後 | main に直接 `docs: archive <作業名>`（内容同一の移動と Status 変更のみのため PR 不要） |
| ルール変更（CLAUDE.md・テンプレ等） | 気づいたとき | 独立した docs PR。進行中の作業ブランチに混ぜない |

補足として次も明文化する。

- 会話中に複数の spec が生まれた場合も、進行中の作業ブランチには置かず、計画用ブランチにまとめて 1 本の docs PR にする
- 進捗の **Branch** は計画時点では予約名。着手時に main から切る

## 範囲外

- ガードによる機械的強制（`specs/guard-protected-paths.md` の範囲）
- アーカイブ操作の自動化（`specs/archive-automation.md` の範囲）
- worktree 運用の詳細（`specs/parallel-worktrees.md` の範囲）

## 失敗時

なし。

## 例

| 操作または入力 | 期待結果 |
|---|---|
| CLAUDE.md を「計画用ブランチ」で検索 | 規約の記述が存在する |
| 新しい spec / progress を作成する | 計画用ブランチの docs PR として main へ入り、実装 PR には spec の新規追加が含まれない |
| 実装 PR のマージ後 | `docs: archive <作業名>` コミットが main に直接積まれる |

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. CLAUDE.md に上記 5 行（新規作成・更新・spec 変更・アーカイブ・ルール変更）のタイミングと行き先がすべて書かれている。`npm run ci` が変更前と同じく成功する。
