# loop-todo-demo

ループエンジニアリング学習用の、フロントエンドTodoアプリ。

## 状態(State)

作業を始める前に必ず `FEATURES.md` を読み、何が終わって何が残っているか把握すること。
タスクを完了したら `FEATURES.md` のチェックボックスと進捗ログを更新すること。
会話やセッションが切れても「前回の続き」から動けるのは、記憶がここにあるから。

## 開発ループ

1. **Plan** — `FEATURES.md` から次の1項目を選び、何をするか1〜3行で宣言する
2. **Implement** — 最小差分で実装する
3. **Verify (自己)** — `verify-frontend-change` スキルの手順を最後まで実行する
4. **Verify (外部)** — `codex-reviewer` サブエージェントにレビューを依頼する
5. **Fix** — Critical 指摘がゼロになるまで 3〜4 を繰り返す
6. **Record** — `FEATURES.md` を更新して報告する

Critical が残っている状態で「完了」と報告しないこと。

## 報告の作法（これが一番重要）

**実行したコマンドの出力を、要約せずに会話に貼ること。**

このプロジェクトでは `/goal` を使う。`/goal` の評価役はツールを実行できず、
会話に出た内容だけを読んで判定する。つまり:

- ❌ 「テストは全部通りました」→ 判定材料にならない（自己申告）
- ⭕️ `npx playwright test` の出力をそのまま貼る → 判定材料になる

「確認した」ではなく「確認した結果」を出すこと。

## 変えてはいけないもの

停止条件を満たすために、以下を書き換えないこと。書き換えれば大抵の条件は「達成」できてしまう。

- `tests/` 配下のテストコードと期待値
- `design-spec.json`（Figmaから抽出した仕様）
- lint / axe の設定ファイル

## コーディング規約

- 依存は最小限（学習用なのでフレームワークなしのvanillaでよい）
- 色・余白・フォントサイズは `src/tokens.css` の CSS 変数のみ使う。ハードコードしない
- インタラクティブな要素はネイティブ要素を使う（div にクリックハンドラを付けない）
