フロントエンドエンジニアのための実習教材

ループの成否は、「done」の書き方で9割決まる。

ループエンジニアリングの教材は、たいてい「自動化の部品」の紹介で終わります。 でも実際にループが壊れる場所は部品ではなく、たった一行の停止条件です。 そしてUIの仕事は「正しい」を言葉で書きたくなる分野なので、ここでいちばん失敗します。 このページは読み物ではなく演習です。手を動かして、その一行を書けるようになるのが目的です。

この教材の主張

ループエンジニアリングとは、「できた」を機械が判定できる形に翻訳する作業である。 部品を並べることではない。翻訳できない仕事は、ループに載せてはいけない。

01

失敗の解剖 — 動いているのに壊れているループ

まず、ありがちな失敗を1本通して見ます。停止条件は一見きちんとしているのに、 3ターン目で自己申告に化けます。矢印ボタンでターンを進めてください。

/goal アクセシビリティの問題を全部直すこと
ここで効いている仕様

評価モデルはツールを実行しない

  1. 評価役は会話に出た内容だけを読む。コマンドを自分で実行したり、ファイルを開いたりはしない
  2. つまり「◯◯が直っている」と実装した本人が書けば、それが判定材料になる
  3. だから停止条件には「何が満たされるか」だけでなく、どうやってそれを会話に出すかまで書く
02

演習 — この停止条件は使えるか

10問。実際にフロントエンドの仕事で書きたくなる停止条件を出します。 「ループに載せられる」か「載せてはいけない」かを選んでください。判定後に理由と修正版が出ます。

Q1 / 10 正解 0

この条件を /goal に渡したら？

こう書く
0
/ 10 問正解

使える停止条件の型

3つの部品が揃って初めて条件になる

  1. 測れる終了状態 — テストの結果、終了コード、件数、スコア。「良くなっている」は状態ではない
  2. 証明の手段 — どのコマンドを叩き、その出力を会話に出すか。ここが抜けると自己申告になる
  3. 変えてはいけないもの — テストコードや期待値を書き換えれば、たいていの条件は「達成」できてしまう
03

翻訳表 — UIの言葉を、測れるものに落とす

演習で身につけるのはこの翻訳です。左が普段レビューで言っていること、右がループに載る形。 右側が書けない項目は、ループではなく自分の目で見る仕事として残してください。それが正しい判断です。

最後の2行が重要です。「デザイン通り」はひとつの塊ではなく、 測れる部分と測れない部分が混ざった言葉です。分けられれば前半はループに載ります。 次のセクションはその分け方の話です。

04

Figmaから実装するフェーズ

「Figma通りに実装して」はそのままでは停止条件になりません。 評価役はFigmaを開けませんし、実装役も毎ターン読み直すとは限らないからです。 ここはフェーズを4つに割って、ループに載る区間と人間が見る区間を先に分けます。

PHASE 1 ループ可

抽出 — Figmaを repo の中の事実に変換する

色・余白・タイポ・variant名・ブレークポイントを design-spec.json に書き出す。 以降のループはFigmaではなくこのファイルを参照します。 停止条件が参照できる実体を、最初に repo の中に作るのがこのフェーズの目的です。

/goal design-spec.json に variant / token / breakpoint の 3セクションが揃い、Figmaのフレーム名と1対1で対応していること
PHASE 2 ループ可

実装 — specに対する網羅と一致で測る

ここが本番のループです。「似ているか」ではなく 「specの全項目に対応物があるか」「値が一致するか」で測ります。 どちらも件数と比較なので機械が判定できます。

/goal design-spec.json の variants 全件に story が存在し、 Playwrightで各storyのcomputed styleがtokenの値と一致。 出力を会話に貼ること。design-spec.json は変更しないこと。 20ターンで止めること
GATE 人間が見る

承認 — ここでループは必ず一度止まる

値が合っていても「デザイン通り」とは限りません。余白のリズム、字面の詰まり、 モーションの気持ちよさは翻訳できない領域です。 ここを通過する条件を書こうとしないこと。 代わりに「ここで止まる」ことを条件に書きます。

/goal 全variantのスクリーンショットを撮って提示し、 私の承認待ちで停止すること（承認そのものは条件に含めない）
PHASE 3 ループ可

固定 — 承認済みの絵をベースラインにする

あなたがOKを出したスクリーンショットを基準画像として保存し、 そこから先はビジュアル回帰テストが効きます。 順序が逆にできない点に注意。承認前にVRTを条件にすると、 実装役が自分で撮った絵を自分の正解にするだけの循環になります。

/goal npx playwright test --grep @vrt が exit 0。 スナップショットの更新（-u）は行わないこと
このフェーズのコツ

4つだけ覚えれば書ける

  1. Figmaを条件の参照先にしない — 先にspecファイルへ抽出し、条件はそのファイルを指す
  2. specを不変条件に入れる — 入れないと、実装に合わせてspecを書き換えて「一致」させられる
  3. 網羅は件数で測る — 「全variant対応」はspecの配列長と実装数の比較に落とせる
  4. VRTは承認の後ろに置く — 承認前のスナップショットは正解ではなく、ただの現状
05

検証役をCodexにする — 正しい繋ぎ方

実装したモデルに自己採点させないために、レビューは別モデルに出します。 ただし繋ぎ方を間違えると、外部レビューの結果が要約で薄まったり、そもそも会話に残らず 停止条件の根拠にできなくなります。よくある実装と、直したものを並べます。

よくある実装

diffをパイプで流し、要約させる

git diff | codex exec --json "レビューして"
→ Haikuが要約して報告

--json はイベントのJSONL列なので解析が不安定。さらに要約層が挟まるぶん、 指摘の具体性（行番号や再現手順）が落ちます。Codexはリポジトリを自分で読めるので、 diffを流し込む必要もありません。

直したもの

ファイルに書かせ、本体が原文を読む

codex exec "git diffの範囲をレビューし
結果を review.md に書け" 
→ 親がReadで原文を読む

レビュー本文がファイルとして残り、親エージェントが要約を経ずに原文を読めます。 さらに停止条件から review.md の中身を参照できるので、 「Criticalが0件」を自己申告ではなく実体に紐づけられます。

この繋ぎ方だから書ける停止条件

外部レビューを、判定可能な形にする

  1. codex-reviewer を実行し、review.md を生成する（生成されたこと自体が会話に残る）
  2. その review.md の全文を会話に出力する（評価役が読めるのはここに出たものだけ）
  3. そこに Critical の行が無い、かつ src 以外が変更されていない
06

層を重ねる — 穴が揃わないように

検証はひとつに絞る必要はなく、薄い層を何枚か重ねるほうが安全です。 ただしスイスチーズモデルの本質は「層を重ねること」ではなく 「穴が揃わないこと」にあります。エージェントのループは、実は穴が揃いやすい構造を持っています。

最大の落とし穴

報告経路が同じなら、何枚重ねても実質1枚

  1. テスト・lint・axe・外部レビューを全部足しても、結果がすべて 「エージェントが書いた会話」を通って判定役に届くなら、経路は1本しかない
  2. その1本が破れた瞬間に、全層が同時に無効化される
  3. 層を足すときは枚数ではなく、既存の層と何が違うかを見る

独立性を測る3軸

AXIS 1

誰が書いた検査か

あなた / エージェント / 第三者のライブラリ / 上流の契約。 実装とテストを同じエージェントが書くと、仕様の誤解がテストにも埋め込まれます。

AXIS 2

何を観測しているか

ソーステキスト / 実行時の振る舞い / 描画結果 / 外部との契約。 全層がソースしか見ていないと、動かすと壊れている、が素通りします。

AXIS 3

誰が判定するか

終了コード（決定的） / 別モデル / 同一モデル / 人間。 実装したモデルが判定を兼ねると、盲点まで共有されます。

2軸以上ずれていれば、独立性はそこそこ期待できます。 逆にlintをもう1つ足すのは3軸とも同じなので、枚数は増えても厚みは増えません。層は数より多様性です。

Claude Codeでの具体的な組み方

/goal と Stop hook は判定の性質が違うので、併用すると経路の相関を切れます。 Stop hook はプロンプトではなくスクリプトを実行できるので、 エージェントの報告を経由せずに自分でテストを走らせて終了コードで判定できます。

判定者観測経路
/goal 小型モデルが判定 会話（エージェント経由）
出力を捏造されると通る
Stop hook シェルの終了コード 帯域外（直接実行）
会話の内容に依存しない

両方が同じ node --test を見ていても、経路が違うので穴は揃いません。 片方だけ緑になったら、報告が実態と食い違っているという強いシグナルで、 これ自体が有用な検知になります。

実務で効く2つのルール

層は、静かに欠落する

  1. 未実行は不合格 — codex が認証切れでエラー →「レビューできませんでした」→ そのまま先へ、が典型。 層が1枚消えたのに誰も気づいていない。証拠が無いことは、問題が無いことではない
  2. 人間が書いた検査を最低1枚 — 受け入れ条件を1本だけ自分でテストに書き、不変条件で保護する。 これだけで「仕様の誤解が全層に伝播する」経路が塞がる

層の順序はコスト順

ミリ秒型チェック
秒単体テスト・静的チェック
数十秒実行 / 描画して確認
分別モデルによるレビュー
分〜時間人間（最も高い層なので最後の1枚）

安く速い層を前に置き、前段で落ちるものを後段まで通さない。 Figmaフェーズで人間ゲートを最後に置いたのも、この並びから自然に出てきます。

07

撤退基準 — ループを止める側の設計

回し始める設計より、止める設計のほうが後回しにされがちです。 ループはトークンを食べながら回り続けられるので、止め方を先に決めておきます。

EXIT 01

ターン上限を条件に含める

条件文の中に「20ターンで止める」と書き込む。無限に粘る余地を最初から与えない。

EXIT 02

同じ失敗が2回続いたら人間へ

評価役の却下理由が2回連続で同じなら、条件の書き方が悪いか、そもそも翻訳できない仕事。

EXIT 03

小さい範囲で試してから広げる

いきなり全ページに回さない。1コンポーネントで費用と挙動を測ってから範囲を広げる。

EXIT 04

そもそも回さない判断を持つ

1〜2往復で終わる仕事にループは不要。翻訳表の右側が書けない仕事も、自分でやったほうが速い。

08

リファレンス

ここから先は暗記するものではなく、必要になったとき引くものです。 4種類は習熟の段階ではなく、仕事の形に合わせて選ぶ分類です。ほとんどの仕事は1番目で足ります。

turn-based
あなたが1往復ずつ。Claude自身が「終わった」と判断して止まる。探索や見た目の判断が要る仕事はこれが正解。検証Skillを書くとここが強くなる
/goal
停止条件を渡し、別の小型モデルが毎ターン判定する。条件が測れるときだけ有効。この教材の演習は全部これのための訓練
/loop
一定間隔で同じプロンプトを再実行。外部の状態を追う仕事向け（PRのレビューコメント、CIの結果）。自分のマシンで動くので閉じれば止まる
/schedule
人が見ていない時間に走らせる。ここまで来たら、翻訳表の右側が全部埋まっていることが前提。埋まっていないなら降りる
worktree
並列で走らせるときに作業コピーごと分離する。複数エージェントが同じdev serverとポートを奪い合う事故を構造的に防ぐ
FEATURES.md
会話をまたぐ記憶。エージェントは毎回忘れるので、記憶はディスクに置く。ここが腐るとループ全体が信用できなくなる
09

最後に

翻訳できない仕事をループに載せない判断も、ループエンジニアリングの一部です。

停止条件が書けないということは、あなた自身もまだ「何ができたら完成なのか」を 決めきれていないということです。それはエージェントの問題ではなく仕様の問題で、 本来あなたが解くべき部分が残っているというサインです。 ループはそこを肩代わりしてくれません。だからこの教材は、 自動化の部品ではなく停止条件の書き方から始めました。
