# レビュー出力の固定スキーマ化と Critical 条件の列挙

レビューサブエージェントの出力を固定スキーマにし、Critical と判定してよい条件をエージェント定義に列挙する。

## 種別

改善

## 対象

- 場所: `.claude/agents/codex-reviewer.md`、`.claude/agents/visual-design-reviewer.md`
- 公開面: Verify (外部) のレビュー結果の形式

## 背景

Verify (外部) は LLM 判定であり、同じ差分でも承認・不承認が揺れうる。往復上限 5 回のガードはあるが、Critical の判定基準自体がレビュアーの裁量に残っている。決定論化の計画（0020〜0025）で選択・開始・形式・判定の大半は機械化されるが、レビューの裁量だけが残る。

2026-08-22 の実測（このセッションで `codex-reviewer` を 6 回実行）:

- subagent トークンの消費が計約 60 万（1 回あたり 8.2 万〜12.9 万）。レビュー出力が自由形式の長文レポートであることが主因
- 6 回のうち 2 回で、ハーネスがレビュー出力を「instruction-shaped pattern (settings-json)」として無害化した（`<` を `` <` `` に置換）。自由形式のレポートに設定ファイル片が含まれると、出力が変形されて届く
- 一方、severity の判定自体は安定していた（`codex-reviewer.md` の「P0・P1 は Critical または High」の対応づけが効いている）。揺れているのは判定ではなく出力の形と量である

現状の `.claude/agents/codex-reviewer.md`（34 行）と `.claude/agents/visual-design-reviewer.md`（28 行）には severity の対応づけと承認条件はあるが、出力スキーマは無い。

backlog 時点で「足りない判断」としていた 3 点への判断（人間、2026-08-22）:

- スキーマの範囲: severity / 根拠のファイルパスと行 / 対応する完了条件番号 / 一文の要約を必須とする。長文の解説は任意の補足欄に寄せる
- Critical の列挙粒度: 列挙外の指摘は自動的に High 以下へ落とす規則にする
- 「テストで書ける指摘はテスト追加の提案として返す」規則: 入れる（レビュー指摘を決定論チェックへ移す漸減の仕組み）

## 仕様

両エージェント定義（`.claude/agents/codex-reviewer.md`、`.claude/agents/visual-design-reviewer.md`）に次を書く。

- **出力スキーマ**: 指摘 1 件ごとに次の 4 項目を必須とする固定スキーマを定義する
  - severity（Critical / High / Medium / Low）
  - 根拠のファイルパスと行
  - 対応する完了条件番号（該当が無ければ「なし」）
  - 一文の要約
  - 長文の解説は任意の補足欄に寄せる。必須項目にしない
- **Critical の列挙**: Critical と判定してよい条件を列挙する。列挙外の指摘は自動的に High 以下へ落とす規則を明記する
  - `codex-reviewer.md`: 少なくとも「完了条件を満たすための期待値改ざん」「仕様の範囲外の実装」「P0 相当の欠陥」を列挙に含む
  - `visual-design-reviewer.md`: 少なくとも「トークン不一致」を列挙に含む（既存の承認節の規則と整合させる）
- **テスト提案規則**: 決定論チェック（テスト・lint）で検証できる指摘は、指摘ではなくテスト追加の提案として返す規則を両定義に書く
- 既存の承認条件（Critical / High がゼロ、5 回上限、Blocked への遷移）と severity 対応づけ（P0・P1 は Critical または High）は変えない

## 範囲外

- レビューの往復上限（5 回）の変更
- レビュー役のモデル指定の変更
- 実際のレビュー出力がスキーマに従うかの検証（LLM の挙動であり、この作業ではエージェント定義の記述までを保証する）
- スキーマ違反を機械的に検知するツールの追加
- 実装コード（`src/`・`tools/`）と `.github/` の変更

## 失敗時

- スキーマに合わない出力: 承認として扱わない（この規則を両エージェント定義に書く）

## 例

| 操作または入力 | 期待結果 |
|---|---|
| `grep -l '完了条件番号' .claude/agents/codex-reviewer.md .claude/agents/visual-design-reviewer.md` | 両ファイルが列挙される（スキーマの必須項目が両定義にある） |
| `grep -c '列挙' .claude/agents/codex-reviewer.md` | `1` 以上（列挙外を High 以下へ落とす規則の存在） |
| `grep -l 'テスト追加の提案' .claude/agents/codex-reviewer.md .claude/agents/visual-design-reviewer.md` | 両ファイルが列挙される |
| トークン表に無い値の使用を検出（レビュー実施時） | Critical（列挙内）として、パスと値つきで返る（範囲外: LLM 挙動のため完了条件にしない） |
| 命名の好みに関する指摘（レビュー実施時） | High 以下として返る（範囲外: LLM 挙動のため完了条件にしない） |

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. 両エージェント定義に、指摘 1 件ごとの必須 4 項目（severity / 根拠のファイルパスと行 / 対応する完了条件番号 / 一文の要約）を定めた出力スキーマの記述がある。`grep 'severity' `・`grep '完了条件番号' `・`grep '一文の要約' ` がそれぞれ両ファイルにヒットすることで検証する。
6. 両エージェント定義に Critical と判定してよい条件の列挙があり、「列挙に無い指摘は High 以下」の趣旨の規則が書かれている。`grep 'High 以下' ` が両ファイルにヒットすることで検証する。
7. 両エージェント定義に「決定論チェック（テスト・lint）で検証できる指摘はテスト追加の提案として返す」趣旨の規則が書かれている。`grep 'テスト追加の提案' ` が両ファイルにヒットすることで検証する。
8. 両エージェント定義に「スキーマに合わない出力は承認として扱わない」趣旨の規則が書かれている。
9. `npm run ci` が成功する。
10. `git diff main --stat` で、`src/`・`tools/`・`.github/` 配下に差分が無い。
