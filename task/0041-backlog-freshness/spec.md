# backlog に実測の定位置を作る

backlog 候補の「現存確認（実測）の日時と結果」に定位置がなく背景の散文に埋まるため、リファインメント時に再測定の要否が判断しづらい。定位置を決める。

## 種別

改善

## 対象

- 場所: `CLAUDE.md` の「仕様」節（backlog spec の「背景」に置く実測行の書式規約を追記する）。あわせて、現存する唯一の backlog 候補 `backlog/0015-playwright-setup-readonly-cache/spec.md` に実測行を適用する
- 公開面: なし（起草・リファインメントの規約）

凍結対象には触れない。`task/TEMPLATE-spec.md` は変更せず、見出しも増やさない（現行規約「見出し名・順番は変えない」を守る）。したがって `allow-protected-change` ラベルは不要である。

## 背景

2026-08-22 のリファインメントでは、昇格判断の前に各候補の前提（対象コードが今もその形か）を人手で再実測し、その結果を依頼文に添えて spec-author へ渡した。実測の日時・手順・出力は spec の背景に散文で混ざるため、次のリファインメントで「いつ時点の観測か」「再測定が要るか」を拾い直すコストが毎回かかる。最終実測日と要点の定位置が 1 行あれば、鮮度の判断が機械的になる。

2026-08-23 のリファインメントで現存を確認した（実測行の定型は未導入のまま。この spec 群の追記も従来どおり背景の散文で行っており、必要性は変わらない）。

2026-08-24 のセッションで backlog 6 件（0036・0037・0038・0039・0040・0041）を昇格した際も、各候補の「いつ時点の観測か」を判断するために、背景の散文から実測記述を人手で拾い直す必要があった。特に `0015-playwright-setup-readonly-cache` は 2026-08-22・2026-08-23 と複数回の実測追記が散文で積み重なっており、最新の状態を読み取るのに spec 全体を読む必要があった。この作業が解こうとしている問題の実例である。なお `0015` は据え置きになった唯一の候補で、据え置き理由（対象環境の `PLAYWRIGHT_BROWSERS_PATH` の実測待ち）も散文の中にある。

## 仕様

- backlog spec の「背景」冒頭、backlog 定型行（「この項目は backlog。着手しない。…」）の直後に、定型の実測行を 1 行置く規約を `CLAUDE.md` の「仕様」節に追記する
- 実測行の書式: `実測: YYYY-MM-DD — <確認した事実の 1 行>`
- リファインメントで再実測したら、この行を**書き換える**（行を積み増さない。履歴は git が持つ）
- 据え置き中の候補は、何の実測を待っているかを確認した事実の 1 行に含めてよい
- 見出しは増やさない（テンプレートの見出し名・順番は変えない、の現行規約を守る）。`task/TEMPLATE-spec.md` は変更しない
- 据え置き中で唯一 backlog に残る `backlog/0015-playwright-setup-readonly-cache/spec.md` には、この書式の実測行を適用する（最終実測日と、据え置き理由である対象環境の `PLAYWRIGHT_BROWSERS_PATH` の実測待ちが 1 行で読めるようにする）

## 範囲外

- 実測の自動化（コードの現存確認をツールで行うこと）
- 既存 backlog 全件への遡及適用（新規・更新分から適用でよい）。ただし `0015` は据え置き中で backlog に残る唯一の候補であり、この作業が解く問題の実例そのものであるため、例外として本仕様の範囲内で適用する

## 失敗時

なし（起草規約であり、実行時の失敗分岐はない）。

## 例

| 操作または入力 | 期待結果 |
|---|---|
| `CLAUDE.md` の「仕様」節を読む | backlog spec の実測行の書式 `実測: YYYY-MM-DD — <確認した事実の 1 行>`・置き場所（「背景」冒頭の backlog 定型行の直後）・更新規則（再実測時は同じ行を書き換える）が読み取れる |
| リファインメント時に `backlog/0015-playwright-setup-readonly-cache/spec.md` の背景を読む | 冒頭付近の `実測:` 行だけで、最終確認日と確認内容（`PLAYWRIGHT_BROWSERS_PATH` の実測待ちで据え置き中であること）が分かる |
| `grep -n '^実測:' backlog/0015-playwright-setup-readonly-cache/spec.md` | 書式 `実測: YYYY-MM-DD — <確認した事実の 1 行>` に合致する行がちょうど 1 行出力される |

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. `CLAUDE.md` の「仕様」節に backlog spec の実測行の規約が書かれており、書式 `実測: YYYY-MM-DD — <確認した事実の 1 行>`・置き場所（「背景」冒頭、backlog 定型行の直後）・更新規則（再実測時は同じ行を書き換え、履歴は git に任せる）の 3 点がいずれも明記されている。`grep -n '実測: YYYY-MM-DD' CLAUDE.md` で書式の記載行が確認できる。
6. `backlog/0015-playwright-setup-readonly-cache/spec.md` の「背景」冒頭（backlog 定型行の直後）に、書式に合致する `実測:` 行がちょうど 1 行あり、最終実測日と据え置き理由（対象環境の `PLAYWRIGHT_BROWSERS_PATH` の実測待ち）が読み取れる。`grep -c '^実測:' backlog/0015-playwright-setup-readonly-cache/spec.md` の出力が `1` である。
7. 凍結対象（`task/TEMPLATE-spec.md` を含む「変えてはいけないもの」の一覧にあるファイル）に変更が無い。`git diff main --name-only` の出力に凍結対象のパスが含まれない。
