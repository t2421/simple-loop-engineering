# ループマニフェストの契約定義

ループエンジニアリングの仕組みを他プロジェクトへ持ち出すために、プロジェクト固有の値を宣言する 1 ファイル（マニフェスト）の契約を定義する。

## 種別

機能追加

## 対象

- 場所: リポジトリ直下のマニフェスト 1 ファイル（新設。名前・形式は昇格時に確定）と、固有値を参照する `tools/*.mjs`
- 公開面: マニフェストの項目（契約）。ツールはこのファイルから固有値を読む

## 背景

このリポジトリのループ（spec 駆動・凍結ガード・Stop hook・アーカイブ）を他プロジェクトで再利用したいが、`tools/*.mjs` に固有値が埋まっており、そのまま持ち出せない。

固有語（`npm` / `package.json` / `calc` / `figma` / `playwright` / `cloudflare`）で `tools/*.mjs` をスキャンした実測は次のとおり。

| ファイル | ヒット | 実体 |
|---|---|---|
| `archive.mjs` | 0 | 完全に汎用 |
| `check-actions.mjs` | 0 | 完全に汎用 |
| `check-progress-coupling.mjs` | 0 | 完全に汎用 |
| `guard-worktree.mjs` | 0 | 完全に汎用 |
| `lint-docs.mjs` | 1 | コメントのみ |
| `stop-hook-ci-dir.mjs` | 2 | コメントのみ |
| `start-task.mjs` | 4 | 全部 `npm ci`（依存導入コマンド 1 概念） |
| `check-protected-paths.mjs` | 8 | ほぼ `package.json` の scripts 読み取り 1 概念 |
| `run-unit-tests.mjs` | 3 | `node --test` の列挙。真に Node 固有 |
| `setup-playwright.mjs` | 5 | 真にプロジェクト固有 |
| `e2e-needed.mjs` | 7 | 真にプロジェクト固有 |

つまりループの骨格はすでに言語非依存で、固有性は数個の名前付き概念に凝集している。この凝集を宣言に切り出せば、ツール本体は汎用のまま持ち出せる。

これは持ち出し 3 部作の 1 つ目である。関連候補: 0043（コア抽出）・0044（2 番目のプロジェクトへの手移植）。

**着手順の注記: 番号順ではなく 0044（2 番目のプロジェクトへの手移植）を先に行う。** 実測された差分がこのマニフェストの項目を決めるため、移植前に契約を確定させると speculative generality になる。

## 仕様

契約の設計判断は次の 4 点である。

1. **プラグイン実行機構は作らない。** ループが検証から必要としているのは「名前・コマンド・終了コード・出力」の 4 つだけである。実行時に差し替わるフック API ではなく、宣言的なマニフェスト 1 ファイルで足りる。
2. **凍結の意味論が唯一の難所。** `check-protected-paths.mjs` が `package.json` の scripts をわざわざ読むのは、凍結の本質が「検証コマンドの中身を書き換えて検証を弱めることを止める」ことだからである。他プロジェクトではその定義は `Makefile`・`pyproject.toml`・`build.gradle` になる。よってマニフェストの verify は「どう検証するか（command）」と「その定義がどのファイルにあるか（definedIn）」の 2 項目を持つ。command だけを設定可能にすると、definedIn 側の書き換えを検知できず凍結が空洞化する。
3. **マニフェスト自身が新しい攻撃面になる。** 現在この仕組みが効いているのは `tools/check-protected-paths.mjs` 自身が保護対象だからである。マニフェストを導入すると「ガードを編集する」代わりに「マニフェストを編集する」で同じ回避ができてしまう。したがってマニフェストは保護パスの筆頭に置く。
4. **e2e・見た目はプラグインではなく任意にする。** `e2e-needed.mjs` は「どの差分が計算ページに影響しうるか」という述語であり、他プロジェクトに対応物が無いことのほうが多い。正しいのは「あれば動く・無ければその工程が存在しない」（省略可能性）であり、空実装を強制する枠（プラグイン可能性）は誤りである。

マニフェストの想定項目:

| 項目 | 内容 |
|---|---|
| install | 依存導入コマンド（現: `npm ci`） |
| verify | 検証コマンド（command。現: `npm run ci`）と、その定義があるファイル（definedIn。現: `package.json`） |
| 条件付き工程 | 名前・コマンド・発火するパス glob の組の一覧（現: e2e）。0 件でもよい |
| 保護パス一覧 | 凍結対象のパス（マニフェスト自身を筆頭に含む） |
| Complexity→モデル表 | `S / M / L` から実装モデルへの対応（現: `S → haiku`、`M → sonnet`、`L → fable`） |
| レビュアーエージェント名 | Verify (外部) で指名するエージェント（現: `codex-reviewer` / `visual-design-reviewer`） |

項目の確定は 0044 の実測を反映してから行う。**0044 の移植先は npm を持たない（パッケージマネージャそのものが無い）ため、上表の `install` が必須項目でよいのかは、この作業の着手時点では未確定である。** 0044 の記録が「対応物なし」を返したなら、`install` は省略可能な項目になる。

## 範囲外

- プラグイン実行機構（実行時に差し替わるフック API）
- ツール本体の汎用パッケージ化・別リポジトリへの切り出し（0043 の範囲）
- 2 番目のプロジェクトへの適用そのもの（0044 の範囲）
- 条件付き工程の空実装の強制
- CLAUDE.md・テンプレート群の持ち出し形式（マニフェストはツールが読む値だけを扱う）

## 失敗時

- マニフェストが存在しない: ツールは黙って既定値で動かず、パスと理由を表示して終了コード非 0 で終わる
- 必須項目の欠落・型不正: どの項目がどう不正かを表示して終了コード非 0 で終わる。**既定値で補わない**
- マニフェストが保護パス一覧に自分自身を含んでいない: 検知して終了コード非 0 で終わる（→「仕様」3）
- マニフェストの `verify.definedIn` が指すファイルが存在しない: 終了コード非 0 で終わる
- マニフェストを `allow-protected-change` ラベル無しで変更する PR: `protected-paths` が検知して CI が落ちる（正しい挙動）

## 例

検証に使う具体例。項目名・ファイル名は着手時に確定させる（下表の `<...>` はその印）。

| 操作または入力 | 期待結果 |
|---|---|
| マニフェストを置いた状態で `npm run ci` | 現在と同じ結果。ツールの挙動が変わらない |
| マニフェストを消して任意のループツールを実行 | 「マニフェストが無い」旨を表示して終了コード非 0 |
| 必須項目（`verify.command`）を消して実行 | 欠落した項目名を表示して終了コード非 0 |
| `verify.definedIn` を存在しないパスにして実行 | そのパスを表示して終了コード非 0 |
| 保護パス一覧からマニフェスト自身を外して実行 | 自己保護の欠落を表示して終了コード非 0 |
| マニフェストを 1 行変える PR をラベル無しで出す | `protected-paths` が失敗する |
| 同じ PR に `allow-protected-change` を付けて再実行 | `protected-paths` が成功する |
| `grep -rn "'npm'" tools/` | 依存導入コマンドのハードコードが 0 件（マニフェスト経由になっている） |

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. リポジトリ直下にマニフェストが 1 ファイル存在し、「仕様」の想定項目表の各項目について、**採用したか / しなかったか**が確定している。採用しなかった項目は spec の「範囲外」に理由とともに書かれている。
6. `task/0044-second-project-port/port-log.md` の観察点それぞれについて、マニフェストの項目に反映されたか、または「項目にしない」判断とその理由が spec にある。**0044 の記録に無い項目を新設していない**（実測に基づかない項目を足さない）。
7. 固有値のハードコードが `tools/` から消えている。少なくとも次が 0 件になる。
   - 依存導入コマンド: `grep -rn "'npm'" tools/`
   - 検証コマンドの定義ファイル名: `grep -rn "package.json" tools/check-protected-paths.mjs`（コメントを除く）
   置き換えられない箇所が残る場合、その理由が spec の「範囲外」にある。
8. マニフェスト自身が保護パスに含まれる。マニフェストを 1 行変える PR がラベル無しで `protected-paths` に落ち、`allow-protected-change` を付けた再実行で成功する。両方の実行結果を進捗に貼る。
9. マニフェストの読み取り・検証を担う純関数にユニットテストがあり、「失敗時」の 5 ケースすべてを覆う。`npm run ci` が緑。
10. 移植先を用意せずに項目を増やしていない。**プラグイン実行機構（実行時に差し替わるフック API）を導入していない。**
