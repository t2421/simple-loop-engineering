# ループマニフェストの契約定義

ループエンジニアリングの仕組みを他プロジェクトへ持ち出すために、プロジェクト固有の値を宣言する 1 ファイル（マニフェスト）の**型と読み取り層**を定義する。**この作業は消費者を持たない。** 各ゲートを宣言から読ませる作業は別に分ける。

## 種別

機能追加

## 対象

- 場所: リポジトリ直下のマニフェスト 1 ファイル（新設）と、その読み取り・妥当性検査を担うモジュール 1 本（新設）。あわせて `tools/check-protected-paths.mjs` にマニフェスト自身を保護対象として加える
- 公開面: マニフェストの項目（契約）と、読み取り層が公開する純関数
- **凍結対象に触れる作業である。** `tools/check-protected-paths.mjs` と本 spec 自身を変更するため、`allow-protected-change` ラベルが要る（下記「失敗時」）

**既存のゲートを宣言から読ませることは、この作業の範囲外である**（→「範囲外」）。

## 背景

このリポジトリのループ（spec 駆動・凍結ガード・Stop hook・アーカイブ）を他プロジェクトで再利用したいが、`tools/*.mjs` に固有値が埋まっており、そのまま持ち出せない。

固有語（`npm` / `package.json` / `calc` / `figma` / `playwright` / `cloudflare`）で `tools/*.mjs` をスキャンした実測は次のとおり。

| ファイル | ヒット | 実体 |
|---|---|---|
| `archive.mjs` | 0 | 完全に汎用 |
| `check-actions.mjs` | 0 | 完全に汎用 |
| `check-progress-coupling.mjs` | 0 | 完全に汎用 |
| `guard-worktree.mjs` | 0 | 完全に汎用 |
| `lint-docs.mjs` | 1 | コメントのみ |
| `stop-hook-ci-dir.mjs` | 2 | コメントのみ |
| `start-task.mjs` | 4 | 全部 `npm ci`（依存導入コマンド 1 概念） |
| `check-protected-paths.mjs` | 8 | ほぼ `package.json` の scripts 読み取り 1 概念 |
| `run-unit-tests.mjs` | 3 | `node --test` の列挙。真に Node 固有 |
| `setup-playwright.mjs` | 5 | 真にプロジェクト固有 |
| `e2e-needed.mjs` | 7 | 真にプロジェクト固有 |

つまりループの骨格はすでに言語非依存で、固有性は数個の名前付き概念に凝集している。この凝集を宣言に切り出せば、ツール本体は汎用のまま持ち出せる。

これは持ち出し 3 部作の 1 つ目である。関連候補: 0043（コア抽出）・0044（2 番目のプロジェクトへの手移植）。

**着手順の注記: 番号順ではなく 0044（2 番目のプロジェクトへの手移植）を先に行う。** 実測された差分がこのマニフェストの項目を決めるため、移植前に契約を確定させると speculative generality になる。0044 は 2026-08-28 に完了・アーカイブ済みで、記録は `task/archive/0044-second-project-port/notes/port-log.md` にある。

### 再スコープ（2026-09-03、人間の判断による改訂）

**改訂の内容**: この作業の範囲を「マニフェストの型と読み取り層」だけに絞る。既存のゲートを宣言から読ませることは 3 つの後続作業へ移す。あわせて「対象」「仕様」「範囲外」「例」「完了条件」を追随させる。

**改訂の理由**: 1 回目の実装（PR #76、2026-08-28。21 ファイル +1963/-188）は Verify (外部) を 5 回回して 5 回とも不承認となり、CLAUDE.md「トークンコスト」の往復上限に到達した。CLAUDE.md は上限超過を「spec か分割の仕方が間違っている」の兆候と定めている。指摘は毎回塞がれ最終状態は Critical 0 / High 1 まで来ていたが、**5 回の指摘はすべて同じ構造だった**。

| 回 | 指摘の構造 |
|---|---|
| 2〜5 | 宣言の型不正・欠落を**既定値で補う**（三項式・`??`・`Array.isArray` だけの検査） |
| 2・4 | **import 側とガード側の 2 実装が非対称**（厳しいほうが import でき、緩いほうが実際にガードを回す） |
| 5 | **宣言した値と実際に使う値の乖離**（`ledger.dir` と `appendOnlyDirs[].prefix` が別値でも通る） |

個別のミスではなく、**1 PR で 6 つのゲート（検証コマンド・保護パス・実装ディレクトリ・台帳・条件付き工程・モデル表）を同時に宣言化したこと**が原因である。消費者ごとに独立して「わざと落とす検査」を持てないため、1 か所塞ぐたびに別の消費者で新しい穴が出た。

**この改訂が検証を弱めない理由**: 完了条件を削っていない。7（ハードコードの消滅）と 8（マニフェスト自身の凍結）のうち、7 は消費者を持つ後続作業へ**移す**（消さない）。8 はこの作業に残す。むしろ「既定値で補わない」を完了条件の中心に据え、1 回目の実装が 5 回にわたって破った不変条件を**この作業だけで機械的に固定する**。範囲が狭くなるぶん、各条件に対する「わざと落とす検査」を実測できる。

**1 回目の実装は捨てない。** ブランチ `feat/0042-loop-manifest`（PR #76、クローズ済み）に `loop.manifest.json`・`tools/loop-manifest.mjs`・2 実装の一致テスト 32 件が残っている。後続の各作業はこれを材料として参照する。

### 0044 の記録からの申し送り（マニフェストの項目に効くもの）

1. **`install` を必須項目にしない。** 移植先 P はパッケージマネージャを持たず、対応物が存在しなかった
2. **`verify.definedIn` を単数にしない。** 「定義の所在」と「呼び出しの所在」の両方が要る。定義だけ守っても、呼ぶのをやめれば検証は消える
3. **`definedIn` の比較は形式非依存にする。** JSON パースを前提にしない。内容の同一性で足りる
4. **実装の指定は prefix だけでは足りない。** ディレクトリと単体ファイルの両方を受ける
5. **作業 ID の形をマニフェスト項目にする。** 4 桁連番は移植元の都合であって契約ではない
6. **前提条件はマニフェスト項目にしない。** 「台帳が同じリポジトリで追跡されている」「台帳が実装より先に base へ入る」は移植可否の判定に属する
7. **台帳の文書構成は単数ではなく許可リストで表す。** `exclude` 単数では移植先の運用を弾く
8. **凍結対象に hook の配線を含める。** 検証コマンドの `definedIn` と同じ構造である

3 件目の移植（2026-09-03、別リポジトリへの導入）で 2 件足りることが分かった。

9. **移植先の既存ワークフローを撤去する場合、導入 PR 自身がゲートに落ちる。** docs PR と実装 PR の 2 本に分ける必要がある（進捗結合は「base に既にある台帳の更新」だけを数えるため）
10. **`allow-protected-change` 相当のラベルが移植先に存在しないことがある。** 作成が要る

## 仕様

契約の設計判断は次の 4 点である。

1. **プラグイン実行機構は作らない。** ループが検証から必要としているのは「名前・コマンド・終了コード・出力」の 4 つだけである。実行時に差し替わるフック API ではなく、宣言的なマニフェスト 1 ファイルで足りる。
2. **凍結の意味論が唯一の難所。** `check-protected-paths.mjs` が `package.json` の scripts をわざわざ読むのは、凍結の本質が「検証コマンドの中身を書き換えて検証を弱めることを止める」ことだからである。他プロジェクトではその定義は `Makefile`・`pyproject.toml`・`build.gradle` になる。よってマニフェストの verify は「どう検証するか（command）」と「その定義がどのファイルにあるか（definedIn）」の 2 項目を持つ。command だけを設定可能にすると、definedIn 側の書き換えを検知できず凍結が空洞化する。
3. **マニフェスト自身が新しい攻撃面になる。** 現在この仕組みが効いているのは `tools/check-protected-paths.mjs` 自身が保護対象だからである。マニフェストを導入すると「ガードを編集する」代わりに「マニフェストを編集する」で同じ回避ができてしまう。したがってマニフェストは保護パスの筆頭に置く。
4. **e2e・見た目はプラグインではなく任意にする。** `e2e-needed.mjs` は「どの差分が計算ページに影響しうるか」という述語であり、他プロジェクトに対応物が無いことのほうが多い。正しいのは「あれば動く・無ければその工程が存在しない」（省略可能性）であり、空実装を強制する枠（プラグイン可能性）は誤りである。

マニフェストの想定項目:

| 項目 | 内容 |
|---|---|
| install | 依存導入コマンド（現: `npm ci`） |
| verify | 検証コマンド（command。現: `npm run ci`）と、その定義があるファイル（definedIn。現: `package.json`） |
| 条件付き工程 | 名前・コマンド・発火するパス glob の組の一覧（現: e2e）。0 件でもよい |
| 実装パス | 「触ったら実装変更とみなす」場所。ディレクトリと単体ファイルの両方を受ける（申し送り 4） |
| 台帳 | 作業ディレクトリの親、作業 ID の形（申し送り 5）、直下に置いてよい文書の**許可リスト**（申し送り 7） |
| 保護パス一覧 | 凍結対象のパス（マニフェスト自身を筆頭に含む） |
| Complexity→モデル表 | `S / M / L` から実装モデルへの対応（現: `S → haiku`、`M → sonnet`、`L → fable`） |
| レビュアーエージェント名 | Verify (外部) で指名するエージェント（現: `codex-reviewer` / `visual-design-reviewer`） |

0044 の実測により `install` は**省略可能な項目**とする（移植先 P に対応物が存在しなかった。背景の申し送り 1）。

### この作業がやること

**マニフェストの型と読み取り層だけを作る。消費者は作らない。**

1. リポジトリ直下にマニフェストを 1 ファイル置き、上表の項目を宣言する。**この時点でどのツールもまだ読まない**
2. 読み取りと妥当性検査を担うモジュールを 1 本置く。公開するのは純関数（読み取り・検査・診断文の組み立て）
3. `tools/check-protected-paths.mjs` にマニフェスト自身を保護対象として加える。**マニフェストを導入すると「ガードを編集する」代わりに「マニフェストを編集する」で同じ回避ができるため、消費者より先にこれを塞ぐ**

### 不変条件: 既定値で補わない

1 回目の実装が 5 回のレビューにわたって破り続けた不変条件である。**この作業の中心に据える。**

- 必須項目の**欠落**を `?? <既定値>` で補わない。欠落は診断して落とす
- **型不正**を無害な値へ化かさない。`=== true` の三項式（`"true"` が false に落ちる）、`Array.isArray` だけの検査（`[42]` を通す）、`?? {}`（綴り違いで検査が消える）はいずれも禁じ手である
- 検査は**葉まで**降りる。配列・入れ子オブジェクトの要素の型を見る
- 診断文は「どの項目が」「どう不正か」を述べる。**読めなかったことを黙って通さない**

### 宣言の内部整合

宣言どうしの食い違いも読み取り層で落とす。1 回目の実装が 5 回目のレビューで指摘された形である。

- 台帳のディレクトリを守る保護エントリが、同じ prefix で存在すること（片方だけ書き換えると、新しい台帳で作業しながら凍結は古いディレクトリを守り続ける）
- 作業 ID のパターンが捕獲グループを 2 つ持つこと（ID と slug。捕獲しない形だと採番も重複検知も無言で壊れる）
- Complexity→モデル表が `S`・`M`・`L` をすべて持つこと（等級を書かない進捗は `M` とみなされるため）

## 範囲外

**既存のゲートを宣言から読ませることは、すべてこの作業の範囲外である。** 消費者ごとに後続の作業へ分ける。

| 移す先 | 中身 | 消費者 |
|---|---|---|
| `0056-manifest-verify-contract` | 検証コマンドの契約（`command` / `definedIn` / `invokedIn`）と保護パス一覧の宣言化 | `check-protected-paths.mjs` |
| `0057-manifest-layout-ledger` | 実装パスと台帳の宣言化。**2 実装の一致テストを完了条件にする** | `check-progress-coupling.mjs` / `guard-worktree.mjs` / `start-task.mjs` |
| `0058-manifest-optional-stages` | 省略可能な項目（条件付き工程・Complexity→モデル表・レビュアー名） | `e2e-needed.mjs` ほか |

そのほか:

- プラグイン実行機構（実行時に差し替わるフック API）
- ツール本体の汎用パッケージ化・別リポジトリへの切り出し（0043 の範囲）
- 2 番目のプロジェクトへの適用そのもの（0044 の範囲。完了済み）
- 条件付き工程の空実装の強制
- CLAUDE.md・テンプレート群の持ち出し形式（マニフェストはツールが読む値だけを扱う）
- **固有値のハードコードを `tools/` から消すこと。** 消費者を持つ後続作業が行う（旧完了条件 7 はそちらへ移した）

## 失敗時

- マニフェストが存在しない: ツールは黙って既定値で動かず、パスと理由を表示して終了コード非 0 で終わる
- 必須項目の欠落・型不正: どの項目がどう不正かを表示して終了コード非 0 で終わる。**既定値で補わない**
- マニフェストが保護パス一覧に自分自身を含んでいない: 検知して終了コード非 0 で終わる（→「仕様」3）
- マニフェストの `verify.definedIn` が指すファイルが存在しない: 終了コード非 0 で終わる
- マニフェストを `allow-protected-change` ラベル無しで変更する PR: `protected-paths` が検知して CI が落ちる（正しい挙動）
- **本 spec の再スコープを含む PR**を `allow-protected-change` ラベル無しで出す: `protected-paths` が `task/0042-loop-manifest/spec.md` と `tools/check-protected-paths.mjs` の変更を検知して落ちる（正しい挙動）。ラベルを付けた再実行で成功する

## 例

検証に使う具体例。項目名・ファイル名は着手時に確定させる（下表の `<...>` はその印）。

| 操作または入力 | 期待結果 |
|---|---|
| マニフェストを置いた状態で `npm run ci` | 現在と同じ結果。**どのゲートの挙動も変わらない**（消費者がまだ無いため） |
| 妥当なマニフェストを読み取り層に渡す | 検査を通り、宣言した値が読める |
| 必須項目（`verify.command`）を消して渡す | 欠落した項目名を表示して落ちる。**既定値で補わない** |
| `verify.command` に数値 `42` を渡す | 型不正として項目名と期待する型を表示して落ちる |
| `implementation.dirs` に `[42]` を渡す | **葉まで検査して**落ちる（配列であることだけを見て通さない） |
| `appendOnlyDirs[].ledger` に文字列 `"true"` を渡す | 型不正として落ちる（三項式で false に化かさない） |
| 綴りを誤った項目名（例: `jsonkey`）を渡す | 未知の項目、または必須項目の欠落として落ちる。`?? {}` で無害な既定に落とさない |
| `verify.definedIn` を存在しないパスにして渡す | そのパスを表示して落ちる |
| 保護パス一覧からマニフェスト自身を外して渡す | 自己保護の欠落を表示して落ちる |
| 台帳のディレクトリを守る保護エントリの prefix を別値にして渡す | 宣言の内部不整合として落ちる |
| 作業 ID のパターンを捕獲グループ 1 つにして渡す | 内部不整合として落ちる |
| Complexity→モデル表から `M` を外して渡す | 内部不整合として落ちる |
| マニフェストを 1 行変える PR をラベル無しで出す | `protected-paths` が失敗する |
| 同じ PR に `allow-protected-change` を付けて再実行 | `protected-paths` が成功する |

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. リポジトリ直下にマニフェストが 1 ファイル存在し、「仕様」の想定項目表の各項目について、**採用したか / しなかったか**が確定している。採用しなかった項目は spec の「範囲外」に理由とともに書かれている。
6. `task/archive/0044-second-project-port/notes/port-log.md` の観察点それぞれについて、マニフェストの項目に反映されたか、または「項目にしない」判断とその理由が spec にある。**0044 の記録に無い項目を新設していない**（実測に基づかない項目を足さない）。背景の申し送り 1〜10 それぞれについて、反映先の項目名か「項目にしない」理由が対応づけられている。
7. **「既定値で補わない」が機械的に固定されている。**「例」の型不正・欠落・内部不整合の各行について、読み取り層が落ちることをユニットテストが覆う。とくに次の 3 つの禁じ手が入り込んでいないことを、**わざと不正な宣言を渡すテスト**で示す。
   - `=== true` の三項式（`"true"` が false に化ける）
   - `Array.isArray` だけの検査（`[42]` が通る）
   - `?? {}` / `?? []`（綴り違い・欠落が無害な既定に落ちる）
8. マニフェスト自身が保護パスに含まれる。マニフェストを 1 行変える PR がラベル無しで `protected-paths` に落ち、`allow-protected-change` を付けた再実行で成功する。両方の実行結果を進捗に貼る。
9. マニフェストの読み取り・検証を担う純関数にユニットテストがあり、「失敗時」の各ケースを覆う。`npm run ci` が緑。
10. 移植先を用意せずに項目を増やしていない。**プラグイン実行機構（実行時に差し替わるフック API）を導入していない。**
11. **消費者を作っていない。** `tools/` のゲート（`check-progress-coupling.mjs`・`guard-worktree.mjs`・`start-task.mjs`・`e2e-needed.mjs`）がマニフェストを読んでいない。`check-protected-paths.mjs` が読むのはマニフェスト自身を保護対象に含めるためだけであり、検証コマンドの定義・実装パス・台帳の判定は従来の定数のままである。
12. この改訂を含む PR を `allow-protected-change` ラベル無しで出すと `protected-paths` が失敗し、ラベルを付けた再実行で成功する。
