# 移植記録: 2 番目のプロジェクトへの手移植

移植先を **移植先 P** と呼ぶ。P の識別子（組織名・リポジトリ名・ホスト名・内部 URL・
クライアント名）はここに書かない（spec「完了条件」7）。

移植は P の **git worktree 上のローカルブランチ**で行い、**push もマージもしていない**。
成果物は「移植された P」ではなく、この記録である。

## 0. 移植先 P の性質（実測）

| 性質 | 実測 |
|---|---|
| パッケージマネージャ | **無い**。`package.json` / `pyproject.toml` / `Package.swift` のいずれも持たない |
| 実装の実体 | シェルスクリプト群、`.mjs` 少数、設定 JSON、Markdown 多数 |
| 検証の定義 | **GitHub Actions のワークフロー YAML に 7 ステップ直書き**。1 コマンドで回す入口が無い |
| テスト | シェルのテスト 1 本（24 ケース）。ランナーによる自動発見も列挙ファイルも無い |
| UI | 無い。e2e・見た目・プレビューに対応物が無い |
| 既存のループ | **ある。** 独自の `CLAUDE.md`、複数フェーズ、クオリティゲート、複数のレビュアーエージェント、`UserPromptSubmit` フック、複数のスキル |
| 台帳 | 作業ごとのディレクトリに要件定義書・設計書・QG 判定ログ。状態は別の JSON |

## 1. 予測との照合（spec「背景」の 4 分類）

移植元の分類は「固有語スキャン」（検索語 `npm` / `package.json` / `calc` / `figma` /
`playwright` / `cloudflare`）に基づいていた。実地の結果は次のとおり。

| 分類 | 予測 | 実測 | 判定 |
|---|---|---|---|
| ヒット 0 = 完全に汎用 | `archive` / `check-actions` / `check-progress-coupling` / `guard-worktree` は無変更で動く | 無変更で動いたのは **`check-actions` の 1 本だけ**。`check-progress-coupling` は「動くが実装パスの大半を見落とす」。`guard-worktree` は定数 2 箇所の差し替えと hook 登録が要った。`archive` は移植しなかった | **ほぼ外れ** |
| コメントのみ | `lint-docs`・`stop-hook-ci-dir` は実質汎用 | `stop-hook-ci-dir` は無変更で動いた。**`lint-docs` は全面改訂が要り、今回は移植しなかった** | **外れ** |
| 1 概念に凝集 | `start-task`（`npm ci`）・`check-protected-paths`（`package.json`） | `check-protected-paths` は 1 概念では済まず **8 箇所**の書き換えが要った（3 節の行 5〜10・22・23） | **外れ** |
| 真に固有 | `run-unit-tests`・`setup-playwright`・`e2e-needed` | 予測どおり。対応物が無いので移植しなかった | **当たり** |

### 外れた理由（分類の方法そのものの誤り）

**固有語スキャンの検索語にレイアウト語（`src/` 等）が入っていなかった。**
言語には依存しないがディレクトリ名には依存するツールが「ヒット 0 = 汎用」に化けた。

最悪の失敗は `check-progress-coupling.mjs` である。**無変更でコピーしても実行でき、
終了コード 0 を返す。** 中身は「`src/`・`tests/`・`tools/` に変更がないため対象外です」である。

P に `src/` と `tools/` は無い。`tests/` だけは**たまたま同じ名前で存在する**ので、
`tests/` を触る差分ではこのチェッカーは発火する。したがって「あらゆる差分が対象外になる」
のではなく、正しくは **P の実装パスの大半（`scripts/`・`schemas/`・`templates/`・`.claude/`・
リポジトリ直下の実装ファイル）が対象外になる**である。貼った出力が示すのも、
その 1 回の試験差分がこの 3 つを含まなかったことまでである。

偶然一致した 1 つがあるぶん、かえって質が悪い。**部分的に発火するので「効いている」ように見える。**

```
--- check-progress-coupling ---
src/・tests/・tools/ に変更がないため対象外です。
exit=0
```

「移植できた」と「ゲートが効いている」は別である。**動くことは移植の証拠にならない。**
`check-protected-paths.mjs` のように明示的に落ちてくれるほうが、はるかに安全だった。

```
--- check-protected-paths ---
fatal: path 'package.json' does not exist in '<base>'
差分を解釈できませんでした: Command failed: git show <base>:package.json
```

## 2. 観察点への回答（spec「仕様」の 7 点）

### 2.1 検証コマンドの定義の所在（`definedIn`）

**P では `definedIn` が 1 ファイルに定まらない。** 検証はワークフロー YAML に直書きされ、
`scripts.ci` に相当する入口が無かった。移植では `scripts/ci.sh` を新設し、YAML は
それを呼ぶだけにした。その結果、凍結すべきものが **2 つ**になった。

- `scripts/ci.sh` — 中身を削れば検証が減る
- `.github/workflows/*.yml` — **`ci.sh` を呼ぶのをやめれば、`ci.sh` を一字も触らずに検証が消える**

> **0042 への含意: `verify` を `{command, definedIn}` の 2 項目にする設計は不足している。**
> `definedIn` は「定義がある場所」だけでなく「その定義が呼ばれている場所」を含む必要がある。
> 最低でも配列にする。移植元では両方が `package.json` と `.github/workflows/` に分かれて
> いたが、後者は `APPEND_ONLY_DIRS` に入っていたので偶然成立していた。

判定の実装は、JSON をパースせず**内容の同一性**で比較する形にした（移植元は
`package.json` の `scripts` オブジェクトを比較していた）。緩い側ではなく強い側に倒した。

### 2.2 依存導入コマンド（`npm ci`）の対応物

**存在しない。** P は依存を持たず、worktree を作った直後に打つコマンドが無い。
移植では呼び出しごと落とした。空コマンドは置かなかった。

> **0042 への含意: `install` を必須項目にしてはならない。** 最初の移植先が既に反例である。
> 省略可能な項目にするか、項目自体を持たない。

### 2.3 テスト列挙（`run-unit-tests.mjs`）の要否

**不要。** P のテストは入口が 1 本（`scripts/test.sh`）で、その中で 24 ケースを回す。
列挙ファイルは要らない。

ただし移植元がこのツールで防いでいた性質（**登録忘れで黙って実行されない**）は
P にも残っている。P では「テスト関数を書いたが `run_test` の行を足し忘れる」で同じことが
起きる。**ツールは不要だが、問題は移植先にも存在する。** ここは今回直していない。

### 2.4 e2e・見た目の工程の省略

**破綻せず省略できた。** P に UI が無く、差分ベースで発火する重い工程も無い。
`e2e-needed.mjs`・`setup-playwright.mjs`・見た目のレビュアーは**ファイルごと置かなかった**。
常に false を返す判定や、何も見ないレビュアー定義は作っていない。

P には時刻起動の重いテストがあるが、差分ベースで発火する条件付き工程ではない。
**対応物ではない。**

### 2.5 `CLAUDE.md` の不変部分と穴

**実際に移植した。** P の `CLAUDE.md` に 4 節を追加し、既存 1 節へ追記した（`+56 行`）。

```
 CLAUDE.md | 56 ++++++++++++++++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 56 insertions(+)
```

#### 書き換え不要だった記述（不変の原則）

| 記述 | P での扱い |
|---|---|
| 実行したコマンドの出力を、要約せずに会話に貼る | **文面ほぼそのまま**移った。宛先だけ P の検証コマンドに変えた |
| レビュアーへ渡すのは差分・対象の完了条件・実測結果だけ | そのまま移った |
| レビュアーはサンドボックス内で検証を再実行しない | **一字も変えずに移った。** 言語にもホストにも依存しない |
| レビューの往復は 5 回を上限 | そのまま移った |
| 手順の知識は CLAUDE.md に足さずスキルへ切り出す | そのまま移った |
| 凍結の一覧に行を足すだけではガードは検知しない | そのまま移った。**移植先でも同じ落とし穴がある** |
| エージェントが自らの判断で凍結対象を書き換えない | そのまま移った |
| 1 worktree = 1 作業 = 1 ブランチ | **移植不要。** P は既に worktree を常用していた |

#### 書き換えた記述

| # | 何を | 何に | なぜ |
|---|---|---|---|
| 1 | `npm run ci` | `./scripts/ci.sh` | 検証コマンドが違う |
| 2 | （移植元に無い規則）| 「検証を足すときは `ci.sh` に足す。ワークフロー YAML へ直接足さない」 | **P 固有の再発防止。** 移植前は YAML 直書きだったので、放っておけば元に戻る |
| 3 | 「Critical が残っている状態で完了と報告しない」 | P の既存節「やってはいけないこと」への 1 行追記。語彙は `🔴` | **新設すると P の QG 判定と二重になる。** 原則は同じでも、置き場は既存節の中が正しい |
| 4 | 「変えてはいけないもの」12 行 | P のパスに合わせた 6 行 | レイアウトが違う。`specs/`・`progress/` の遺物は落とした |
| 5 | 「このプロジェクトでは `/goal` を使う」 | 落とした | P に評価役の仕組みが無い |
| 6 | 開発ループの 7 工程 | **移植しなかった** | P の Phase 0〜4 が対応物。置き換えると既存の運用を壊す（2.6 c） |

#### 移植して分かったこと

**最も価値が高かったのは「報告の作法」だった。** P には「出力を貼る」に相当する規定が
無く、QG の判定（🟢🟡🔴）が根拠の出力を伴わないまま書かれうる状態だった。
`loop-port` スキルが「移植で最初に削られやすく、削るとループが動いて見えて何も
検証していない状態になる」と書いていたのは、実地で正しかった。

**逆に、置き場の判断が難しかったのは「Critical ゼロ」である。** 原則としては不変だが、
P には既に同じ構造（🔴 は 3 回まで再実行、超えたら人間に判断を仰ぐ）があった。
節を新設せず既存節へ 1 行足すのが正しく、**「不変の原則だからそのまま移す」では誤る。**
移植は「文面を移す」ことではなく「既にあるものを見つけて、無いものだけ足す」ことだった。

### 2.6 既存の運用との衝突

**これが最大の発見である。5 件あった。** 最初の 3 件は自力で、(d)(e) は外部レビューで見つかった。

#### (a) 台帳が git 管理外だった

P の `.gitignore` は台帳ディレクトリを丸ごと除外していた。

```
docs/workflow/tasks.json
docs/workflow/*/
```

**凍結ガードも進捗結合の検査も git の差分を見る。** 追跡されていないものは差分に現れず、
どちらのゲートも原理的に成立しない。移植では `.gitignore` を変更して台帳を追跡対象にした。

これは**技術的な修正ではなく方針変更**である。台帳には要件定義書・設計書が入るので、
追跡すれば顧客固有情報がリポジトリに載る。除外は意図的だった可能性が高い。

> **0042・0043 への含意: ループは「台帳が実装と同じリポジトリで追跡されている」ことを
> 前提にしている。この前提はマニフェストの項目ではなく、移植の可否そのものを決める
> 前提条件である。** 満たせない移植先では、ゲート層は移植できない。

#### (b) 凍結の方式が正面から衝突した

P には既に凍結があった。ただし**差分ベースのガードではなく、テストである。**
「ワークフロー YAML が各検証コマンドを literal に含むこと」を `grep -Fq` で固定していた。

移植元の設計（検証を 1 ファイルに集約し、そのファイルを凍結する）は、
**P の設計（YAML への直書きをテストで固定する）を破壊する。** 実際に破壊した。

```
not ok - parent CI has quality and secret gates
Tests: 24, Failures: 1
```

origin/main では `Tests: 24, Failures: 0` なので、移植による退行である。

解いた方法: **不変条件（検証を黙って外せない）を保ったまま、追随先を移した。**
テストが見る先を「YAML の中身」から「YAML が `ci.sh` を呼んでいること **かつ**
`ci.sh` が各検証を含むこと」の 2 段に変えた。片方だけ見ると、
YAML だけ → `ci.sh` を空にして通せる、`ci.sh` だけ → 呼ぶのをやめて通せる。

修正後、P のテストは緑に戻った。

```
ok - local Markdown links resolve

Tests: 24, Failures: 0
```

そのテストは移植後の設定では保護対象（`tests/`）なので、この修正自体が
`allow-protected-change` を要求する。**ガードが設計どおりに働いた。**

#### (c) P の Phase 0 ゲートと、移植したループの開始手順が二重になる

P は「作業依頼を受けたら実作業前に必ず外部の台帳に起票する」ことを必須ゲートにしている。
移植元の Plan 工程（`start-task` で次の 1 作業を選ぶ）とは**別の入口**である。
今回は `start-task` を移植しなかったため衝突は顕在化しなかった。

> **0043 への含意: Core を「作業台帳の層」と「ゲートの層」に分けるべきである。**
> P には台帳の層が既にあり（フェーズ・QG・タスク管理）、無いのはゲートの層だった。
> 一体で配ると、既にあるものを置き換えることになる。この 2 層は独立して移植できる。

#### (d) 台帳のライフサイクルが噛み合わない（未解決）

進捗結合の検査は「**base に既にある**台帳の内容を書き足した更新」だけを数える。
新規作成を数えないのは、実装と同じ PR で台帳を作れば結合が自明に成立してしまい、
ゲートの意味が消えるからである。移植元はこれを「台帳は先に計画用ブランチの docs PR で
入れる」という運用で満たしている。

**P にその運用は無い。** P は最初のフェーズで台帳を作り、その後にブランチを切る。
つまり台帳は実装ブランチ上で新規作成される。移植先で通常の実装 PR を模した実測:

```
実装（…）を変更していますが、進行中の作業の
台帳（docs/workflow/<日付>_<slug>/QG_log.md）の更新が含まれていません。
…
次の変更は、その形でないため数えていません:
  - docs/workflow/2026-08-28_normal-task/QG_log.md
（新規追加・削除・種別の変更（symlink への置き換えなど）・移動）
exit=1
```

**P の標準フローに従うかぎり、あらゆる実装 PR がこのゲートで落ちる。**
4 節 (b) の実測で「通る」側を示した base は、`Branch:` 行を手で書いた**手作りの台帳**である。
P のテンプレートに `Branch:` 行は無い。CI 経路は base 側の `Branch:` を読むので、
仮に新規作成を数えたとしても `（行がありません）` で別作業扱いになる。

解き方は 2 つある。**どちらも取っていない。** 未解決として記録する。

1. **P に「台帳を先に入れる」工程を足す。** ゲートは無傷だが、P のフェーズ運用を変える
2. **新規作成も数えるようにチェッカーを緩める。** 運用は変わらないが、**ゲートが弱まる**。
   実装と台帳を同じ PR で作れば必ず通るので、結合の検査として意味を失う

**2 を選ばなかった理由を明記しておく。** 移植先で落ちるからといって判定を緩めるのは、
このループが最も禁じている操作（停止条件を満たすためにゲートを書き換える）そのものである。

> **0042 への含意: 「台帳が追跡されていること」（(a)）に加えて、
> 「台帳が実装より先に base へ入ること」も移植の前提条件である。**
> どちらもマニフェストの項目ではなく、移植可否の判定に属する。

#### (e) 「別名 spec 禁止」が P の台帳構成と衝突した

移植元の台帳は 1 作業 1 spec なので、「直下の `.md` は `spec.md` と `progress.md` だけ」
という**単数の除外**で足りていた。P の台帳は規模に応じて 5 種類の文書を持つ。

単数の除外のまま移植すると、設計書や実装計画を足す通常の PR が毎回
`allow-protected-change` を要求する。**ラベルが日常化すればガードは形骸化する。**

**許可リスト（複数）に変えて解いた。** 実測:

```
01_requirements.md           ok
02_design.md                 ok
03_implementation_plan.md    ok
04_e2e_test_plan.md          ok
QG_log.md                    ok
notes.md                     VIOLATION: 仕様は 01_requirements.md だけにする（別名の spec で Target Spec を付け替えて凍結を迂回できる）
```

許可リストに無い名前は従来どおり弾かれるので、**迂回経路は開いていない。**

（この作業自身、記録の置き場が移植元の「別名 spec 禁止」に触れて凍結改訂を出している。
**同じ規則が、移植元では起草者を、移植先では既存運用を刺した。**）

### 2.7 `loop-port` カタログ（13 グループ）の過不足

| 節 | 実地での評価 |
|---|---|
| 2.1 検証コマンドの契約 | **不足**。`definedIn` を単数で書いていた。「定義の所在」と「呼び出しの所在」の 2 つが要る（2.1 参照） |
| 2.2 実装ディレクトリの名前 | **不足**。ディレクトリだけを想定していたが、P はリポジトリ直下の単体ファイル（`setup.sh` 等）が実装だった。prefix 判定に単体ファイルの列を足す必要があった |
| 2.3 依存導入コマンド | 妥当。「不要なら呼び出しごと落とす」がそのまま正しかった |
| 2.4 テストの列挙 | 妥当。「ランナーが自動発見するなら要らない」がそのまま正しかった |
| 2.5 条件付き工程 | 妥当。「対応物が無ければファイルごと消す」がそのまま正しかった |
| 2.6 保護対象の再定義 | 妥当だが**手数を過小評価**。「1 概念」ではなく 8 箇所。うち 2 箇所は外部レビューでしか見つからなかった |
| 2.7 モデルルーティング | 今回対象外（`start-task` を移植せず） |
| 2.8 レビュアー | 今回対象外。P には既にレビュアー 6 種がある |
| 2.9 ホストの前提 | 妥当。P も GitHub なので差し替え不要だった（**この移植では検証できていない**） |
| 2.10 hook と権限 | 妥当。Stop hook の構造はそのまま移った |
| 2.11 lint の型と固定文字列 | **不足**。下記「新規」を参照 |
| 2.12 `CLAUDE.md` | 妥当。ただし「既存の `CLAUDE.md` があるとき」の記述が無い（2.6 c） |
| 2.13 持ち出さないもの | **妥当。ただし今回は従わなかった。** 「ループのツール自身のテストは持ち出す」という指示に反してテストを置かず、その結果ゲートの取りこぼしを実行するまで発見できなかった（→ 5 節「0043 へ」3） |
| **新規: 定数を差し替えても文言は追随しない** | カタログに無い。実測で**3 回**踏んだ |
| **新規: 台帳が追跡されていること** | カタログに無い。移植の前提条件（2.6 a） |
| **新規: 移植先に既存のループがある場合** | カタログに無い。置き換えではなく対応づけが正しい（2.6 c） |
| **新規: Stop hook の終了コード** | カタログに無い。止めるのは exit 2 である（下記） |

**不要だった項目: 無し。** カタログ 13 グループのうち「この移植先には要らなかった」と
判定できたものは 1 つも無い。2.7・2.8 の 2 件は**今回の移植範囲に入れなかった**だけで、
不要と判定したわけではない（`start-task` を移植すればモデル表もレビュアーも要る）。

#### 新規項目「定数を差し替えても文言は追随しない」

`check-progress-coupling.mjs` の定数（`IMPLEMENTATION_DIRS`・`TASK_DIR`・`PROGRESS_FILE`）を
差し替えても、利用者に見える文言には旧語彙が残った。3 回に分けて発見した。

1. 1 回目の実測で `progress.md（task/<id>-<slug>/progress.md）` が出た
2. 直したあと `更新された progress.md が…` `task/<name>/progress.md` が出た
3. さらに直したあと、**成功時**のメッセージに `progress.md` が残っていた

さらに 4 回目・5 回目があった。外部レビューが `foreign`（別作業のブランチ）経路の文言と、
`guard-worktree` が案内する「移植していないコマンド」を見つけた。

**エラー経路だけ直しても足りない。** 成功時の文言も、めったに通らない分岐の文言も見る。
定数の差し替え漏れは「動くが誤ったことを言う」形で残り、テストは通る。
**この項目を記録に書いた後も、同じ罠に 2 回落ちた。** 人手で潰す限り漏れる。
機械化（利用者向け文字列リテラルに対する禁止語の走査）が要る。

## 4. ゲートが「落ちること」の実測

### (a) 凍結ガード — 保護パスを 1 行変える

```
=== (a) 凍結ガード: 保護パスを 1 行変える ===
保護パスの変更を 1 件検知しました:
  - scripts/test.sh: 検証の委譲先は変更も移動もできない

変更が正当なら、改訂内容と理由を spec に書いたうえで PR に allow-protected-change ラベルを付けてください。
exit=1
--- allow-protected-change ラベルを付けた場合 ---
保護パスの変更を 1 件検知しました:
  - scripts/test.sh: 検証の委譲先は変更も移動もできない

ラベル allow-protected-change があるため通過させます（人間による明示承認）。
exit=0
```

### (b) 進捗結合 — 実装を触って台帳を更新しない

```
=== (b-1) 実装を触って台帳を更新しない ===
実装（scripts/・tests/・schemas/・templates/・.claude/・setup.sh・repos.json）を変更していますが、進行中の作業の
台帳（docs/workflow/<日付>_<slug>/QG_log.md）の更新が含まれていません。
工程を進めたら、その作業の QG_log を同じ PR で更新してください。
数えるのは、base に既にある QG_log.md の内容を書き足した更新だけです。
この PR で新しく作った QG_log.md は数えません。要件定義書 + QG_log は
先に計画用ブランチの docs PR で main へ入れてください。

作業に紐づかない変更なら、PR に no-progress-needed ラベルを付けてください（人間が付ける）。
exit=1

=== (b-2) 同じ差分に台帳の追記を足す ===
実装の変更に、進行中の作業の progress.md がちょうど 1 件伴っています。
  作業: 2026-08-27_loop-port
exit=0
```

（b-2 の出力に残る `progress.md` が、2.7 の新規項目で述べた 3 回目の残存である。
この実測のあとに修正した。）

> **(b-2) の base は手作りである。** `Branch:` 行を手で書いた台帳を base に置いて測った。
> **P の標準フローでは同じ差分が落ちる**（2.6 d）。ここで示せているのは
> 「判定器が正しく通す条件」であって「P の日常の PR が通る」ではない。

### (c) Stop hook — 検証を意図的に壊す

**移植の途中で、この機構の終了コードに穴があることが分かった。**

移植元の Stop hook は `... && npm run ci 1>&2 && ... check-actions.mjs` という形で、
検証が落ちるとコマンド全体が **exit 1** で終わる。ところがこの仕組み自身、
`check-actions.mjs` の中で「止める」ときだけ **exit 2** を使い分けている。

```
198:    exit: 2,
344:    process.exit(2);
```

exit 1 は「非ブロッキングのエラー」であり、表示はされるが止まらない。
つまり **「検証が落ちたときに止める」経路だけが、止まらない終了コードを返していた**。
移植先では検証失敗を exit 2 に直したうえで測った。

```
=== (c-1) 健全なとき ===
Stop hook exit=0
ci: all checks passed
check-actions: HEAD がリモートに無いため（未 push）、判定しません。

=== (c-2) 検証を壊したとき ===
Stop hook exit=2（2 = セッションをブロックする）

=== Validate repository registry ===
registry check deliberately broken
```

hook の登録内容（`.claude/settings.json` の実測。**この登録が無ければ、上のコマンドが
exit 2 を返してもセッションには何も起きない**）:

```
PreToolUse: matcher=Write|Edit
  command: node "$CLAUDE_PROJECT_DIR/scripts/loop/guard-worktree.mjs"
Stop: matcher=(なし)
  command: INPUT="$(cat)" && CI_DIR="$(printf %s "$INPUT" | node "$CLAUDE_PROJECT_DIR/scripts/loop/stop-hook-ci-dir.mjs")" && cd "$CI_DIR" && { ./scripts/ci.sh 1>&2 || exit 2; } && printf %s "$INPUT" | node "$CLAUDE_PROJECT_DIR/scripts/loop/check-actions.mjs"
```

**測ったのは hook コマンド単体の終了コードである。** 実セッションがブロックされる
トランスクリプトまでは採っていない。上の登録内容は、その間接証拠として貼っている。


> **移植元への申し送り（この作業では直さない。範囲外）:** 同じ穴が移植元の
> `.claude/settings.json` にもある。`npm run ci` が落ちたときの Stop hook の
> 終了コードは 1 であり、`check-actions.mjs` が使う 2 と食い違う。
> **backlog に起票すべきである。**

3 つとも「**落ちること**」を実測できた。省略したゲートは無い。

ただし (b) については、**落ちる側だけが P の実運用と一致している。**
通す側は手作りの base でしか示せていない（2.6 d）。

## 5. 後続への申し送り

### 0042（マニフェスト契約）へ

1. **`install` を必須項目にしない。** 最初の移植先が反例である（2.2）
2. **`verify.definedIn` を単数にしない。** 「定義の所在」と「呼び出しの所在」の両方が要る（2.1）
3. **`definedIn` の比較は形式非依存にする。** JSON パースを前提にしない。内容の同一性で足りる
4. **実装の指定は prefix だけでは足りない。** ディレクトリと単体ファイルの両方を受ける（3-12）
5. **作業 ID の形をマニフェスト項目にする。** 4 桁連番は移植元の都合であって契約ではない（3-14）
6. マニフェスト項目にできない**前提条件**が 2 つある。**台帳が同じリポジトリで追跡されていること**（2.6 a）と、**台帳が実装より先に base へ入ること**（2.6 d）。どちらもマニフェストで表現するものではなく、移植可否の判定である
7. **台帳の文書構成は「単数の spec + 単数の progress」ではない。** 許可リスト（複数）で表す。`exclude` 単数では移植先の運用を弾く（2.6 e）
8. **凍結対象に「hook の配線」を含める。** 判定コードだけ守っても、呼び出し側（`.claude/settings.json` に相当するもの）を落とせばゲートは呼ばれない。検証コマンドの `definedIn` と同じ構造である

### 0043（コア抽出）へ

1. **Core を「台帳の層」と「ゲートの層」に分ける。** P には前者が既にあり、無いのは後者だった。一体で配ると既存の運用を置き換えることになる（2.6 c）
2. **配布形態を npm パッケージにしない。** P に npm は無い。`.mjs` のファイル群をそのまま置ければ動いた。単一ディレクトリのコピー（`git subtree` かインストールスクリプト）で足りる
3. **移植したツールにはテストを伴わせる。** 今回は移植先にテストを置かなかったため、`check-progress-coupling` が **P の実装パスの大半を対象外にする**状態を、実行してみるまで気づけなかった（1 節。`tests/` だけは偶然一致して発火するので「常に通る」ではない）。ゲートを配ってテストを配らないと、移植先で誰も効果を確かめていない状態になる
4. **利用者向け文言を定数から生成する。** 手で書いた文字列は定数の差し替えに追随しない（2.7 新規項目）
5. **「検証がファイルを書き換えたか」はステータスではなく内容で見る。** `git status --porcelain` の
   前後比較では、既に `M` と出ているファイルの再変更を取りこぼす（3-4）
6. **ゲートを配るときは「適合テスト」を 4 本伴わせる。** 今回の取りこぼしはすべて
   外部レビューでしか見つからなかった。テストがあれば移植の時点で落ちた。
   - **A レイアウト適合**: 宣言した実装パス全件が判定器で対象になり、非実装が対象外になる
   - **B 配線の保護**: hook から呼ばれるファイルのうち、保護集合に無いものが 0 件
   - **C 語彙の残存**: 利用者向け文字列リテラル（`console.error` / `console.log` の実引数）に
     移植元の語彙（`progress.md`・`task/`・`npm run ci`・`tools/`）が 0 件。コメントは対象外
   - **D 台帳文書の許可**: 台帳テンプレートが定める文書名全件が、別名 spec 判定で違反にならない

### `loop-port` スキルへ

カタログに **4 項目**の追加が要る（2.7 の表で **新規** と記した 4 件）。
この記録では改訂しない（spec「範囲外」）。

1. 定数を差し替えても利用者向け文言は追随しない
2. 台帳が同じリポジトリで追跡されていること（移植の前提条件）
3. 移植先に既存のループがある場合は、置き換えではなく対応づけ
4. Stop hook の終了コード（止めるのは 2。1 は非ブロッキング）

## 6. 移植先 P に残したもの

- ローカルの worktree 1 つとブランチ 2 本。**push もマージもしていない**
- P のプライマリチェックアウトには触れていない（worktree は P の gitignore 済みディレクトリ配下）
- 撤去は worktree の削除とブランチの削除だけで済む
- P のリモートには一切影響していない（`git push` を実行していない）

**レビュー経路の注意（記録として残す）:** 外部レビュアーの生ログには P のローカル絶対パス
（組織名・リポジトリ名を含む）と P のファイル本文が入る。**この記録や PR 本文へ
そのまま貼ると、ファイル側の匿名化が成立していても会話経路で破れる。**
貼るのは判定ブロックだけにし、絶対パスは伏せる。完了条件 7 は「作業ディレクトリの中身」を
見ているので、この経路は検知できない。
