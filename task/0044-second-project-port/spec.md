# 2 番目のプロジェクトへの手移植

ループエンジニアリングの仕組み（`tools/*.mjs`・`CLAUDE.md`・`task/` の構造）を、npm を使わない 2 番目のプロジェクトへ**手で**移植し、書き換えが必要だった箇所を記録する。

## 種別

その他（実測・調査。抽象化に先立つ手移植）

## 対象

- 場所: 移植元はこのリポジトリのループ機構全体（`tools/*.mjs`・`CLAUDE.md`・`task/` / `backlog/` の構造・`.github/workflows/`）。移植先は**別組織の private リポジトリ 1 件**（以下「移植先 P」）
- 公開面: なし。成果物は「移植されたプロジェクト」ではなく**書き換え箇所の記録**である。記録の置き場は `task/0044-second-project-port/notes/port-log.md`

移植先 P の性質（この 4 点がこの作業にとっての移植先の定義である）:

| 性質 | 内容 |
|---|---|
| パッケージマネージャ | **無い**。`package.json` も `pyproject.toml` も `Package.swift` も持たない |
| 検証の実体 | シェルスクリプト群（`bash -n` / ShellCheck / 自作の検査スクリプト）と、少数の `.mjs` |
| 検証コマンドの定義 | **GitHub Actions のワークフロー YAML に直書き**。`scripts.ci` に相当する 1 コマンドが存在しない |
| e2e・見た目 | UI を持たないため**該当なし** |

**移植先 P の識別子（組織名・リポジトリ名・ホスト名・内部 URL・クライアント名）はこのリポジトリに書かない。** このリポジトリは public で、移植先 P は private である。記録は性質と対応関係だけを残す（→「完了条件」7）。

## 背景

ループエンジニアリングの仕組みを他プロジェクトへ持ち出す 3 部作（0042 マニフェスト契約・0043 コア抽出・0044 本候補）のうち、**最初に着手すべき**候補である。番号は 0044 だが、着手順は 0042・0043 より**先**とする。

中心的な主張: **2 つ目のプロジェクトが存在する前に抽象化しない。** 現在の設計は「計算ウェブアプリ 1 件」からの一般化であり、そのまま契約（マニフェスト項目・コアの切り出し線）を決めると speculative generality になる。1 回の手移植のコストは、間違った抽象化を後から剥がすコストよりはるかに小さい。

実測（2026-08-23、`tools/*.mjs` の固有語スキャン。検索語は `npm` / `package.json` / `calc` / `figma` / `playwright` / `cloudflare`）:

- ヒット 0（完全に汎用）: `archive.mjs`、`check-actions.mjs`、`check-progress-coupling.mjs`、`guard-worktree.mjs`
- コメントのみ: `lint-docs.mjs`（1 件）、`stop-hook-ci-dir.mjs`（2 件）
- 1 概念に凝集: `start-task.mjs`（4 件、すべて `npm ci`）、`check-protected-paths.mjs`（8 件、ほぼ `package.json` の scripts 読み取り）
- 真に固有: `run-unit-tests.mjs`（3 件）、`setup-playwright.mjs`（5 件）、`e2e-needed.mjs`（7 件）
- `CLAUDE.md` の固有語: 23 件（2026-08-27 の再測では 22 件）

この予測（＝書き換えが要るのは上記の固有側だけで、骨格はすでに言語非依存である）が実際に当たるかを、移植で検証するのがこの候補の価値でもある。

### 移植先の選定（2026-08-27 に確定）

backlog の時点では「Swift か Python」を想定していたが、**移植先 P は Bash 主体でパッケージマネージャを持たない**。当初の想定とは違うが、選定の**意図**（「同じ Node を選ぶと言語結合が露出せず、移植できたように見えてしまう」）はより強く満たす。

- `npm ci` に相当する依存導入コマンドが**そもそも存在しない**。0042 が「install」を必須項目に置こうとしていた前提を、最初の 1 件で反証しうる
- 検証コマンドの定義が**ワークフロー YAML そのもの**である。`check-protected-paths.mjs` が `package.json` の `scripts` を読む設計が、`definedIn` という 1 項目で本当に一般化できるのかがここで試される
- テストがシェルスクリプト 1 本で、ランナーによる自動発見も `node --test` の列挙も無い。`run-unit-tests.mjs` の「そもそも要るか」が実測できる
- UI が無いので、e2e・見た目・プレビューの 3 工程を**省略してループが回るか**を実際に確かめられる

### 凍結改訂（2026-08-27、着手後の spec 変更）

**改訂の内容**: 記録の置き場を `task/0044-second-project-port/port-log.md` から
`task/0044-second-project-port/notes/port-log.md` へ移す。

**理由**: 起草時に指定した置き場が、このリポジトリ自身の凍結ガードに触れる。
`tools/check-protected-paths.mjs` の `isAliasSpec` は、作業ディレクトリ**直下**の
`.md` のうち `spec.md`・`progress.md` 以外を「別名 spec」として禁じる。
Target Spec を別名の spec へ付け替えて凍結を迂回する経路を塞ぐための規則である。
実測:

```
保護パスの変更を 1 件検知しました:
  - task/0044-second-project-port/port-log.md: 仕様は spec.md だけにする（別名の spec で Target Spec を付け替えて凍結を迂回できる）
```

**これが検証を弱めない理由**: `isAliasSpec` は作業ディレクトリ直下だけを見る。
`notes/` 配下は「関連文書」として `APPEND_ONLY_DIRS` の保護を受けたまま、別名 spec の
禁止には触れない。**保護は弱まらず、迂回経路も開かない。** 直下に置いたまま
`allow-protected-change` で押し通すほうが、別名 spec 禁止という規則そのものを
形骸化させるため危険である。

### 先行して整備済みのもの

`.claude/skills/loop-port`（PR #72、2026-08-27 マージ）に、変更箇所のカタログ（13 グループ）と各箇所の埋め方の方針がある。**この作業は、そのカタログが実地で正しいかを検証する最初の 1 件でもある。** 記録はカタログの節番号に対応づけて書く。

## 仕様

手順の骨子:

1. **意図的に npm を使わないプロジェクト**（移植先 P）を 2 番目の適用先にする。同じ Node を選ぶと言語結合が露出せず、移植できたように見えてしまう
2. そこへ手で移植する。**共通化・自動化はしない。** マニフェスト（0042）もパッケージ化（0043）もこの作業では作らない
3. **書き換えた箇所を 1 件ずつ記録する。** ファイル・行相当の粒度で「何を」「何に」「なぜ」を残す。この記録が 0042 のマニフェスト項目の原資料になる

移植で特に観察し、記録に含める点:

- `check-protected-paths.mjs` の「検証コマンドの定義がどのファイルにあるか」が、移植先 P で何に相当するか。P では**ワークフロー YAML に直書き**なので、`definedIn` が「マニフェストの中身を読むファイル」ではなく「ワークフローそのもの」になる。この場合に凍結が成立するか
- `start-task.mjs` の依存導入コマンド（`npm ci`）に**対応物が無い**場合、呼び出しごと落として破綻しないか
- `run-unit-tests.mjs` のテスト列挙が、移植先の慣習でそもそも必要か
- e2e・見た目の工程が移植先に**存在しない**場合、ループが破綻せず省略できるか
- `CLAUDE.md` のどの記述が書き換え不要（不変の原則）で、どこが穴（プロジェクト固有）だったか
- 移植先 P は**すでに独自の `CLAUDE.md` と `.claude/` を持つ**。既存の運用と衝突した箇所と、その解き方
- `.claude/skills/loop-port` のカタログ 13 グループのうち、**実地で不足していた項目・不要だった項目**

記録は、背景の実測（汎用 / コメントのみ / 1 概念に凝集 / 真に固有）の分類と突き合わせ、予測が当たった箇所・外れた箇所を明示する。

## 範囲外

- 抽象化・共通化の設計と実装（0042 マニフェスト契約・0043 コア抽出でやる）
- 移植ツール・スクリプトの作成（手移植が前提。自動化しない）
- npm を使う Node 製プロジェクトへの移植（言語結合が露出しないため対象外）
- 移植先プロジェクトのアプリケーション機能そのものの開発
- このリポジトリ側の `tools/*.mjs`・`CLAUDE.md` の書き換え
- 移植先 P への PR のマージ（移植先の運用主体の判断であり、この作業の完了条件にしない）
- `.claude/skills/loop-port` の改訂（不足が見つかったら記録に残すにとどめる。改訂は別作業）

## 失敗時

- 上記「凍結改訂」を含むこの PR を `allow-protected-change` ラベル無しで出す:
  `protected-paths` が `spec.md` の変更を検知して CI が落ちる（**正しい挙動**）。
  ラベルを付けた再実行で成功する

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. `task/0044-second-project-port/notes/port-log.md` が存在し、次をすべて含む。
   - 「仕様」の観察点 7 つすべてについて、移植先 P での対応物、または「対応物なし」とその扱いが 1 項目以上ある
   - 背景の 4 分類（汎用 / コメントのみ / 1 概念に凝集 / 真に固有）ごとに、**予測が当たったか外れたか**が明示されている。外れた項目は理由を書く
   - `.claude/skills/loop-port` のカタログ 13 グループのうち、実地で**不足していた項目・不要だった項目**の一覧（無い場合は「無し」と明記）
6. 移植先 P で、ループのゲートが**落ちること**を実測した出力が `notes/port-log.md` にある。次の 3 つすべてを含む。
   - 保護パスを 1 行変える変更に対し、凍結ガード相当が失敗する
   - 実装ディレクトリを触って progress を更新しない変更に対し、進捗結合の検査相当が失敗する
   - 検証コマンドを意図的に壊した状態で、Stop hook 相当がセッションを止める
   3 つのうち移植先で**成立させなかったゲート**があれば、その理由を書けば満たしたものとする（省略の記録も実測である）。
7. `notes/port-log.md` と `spec.md`・`progress.md` に、移植先 P を特定できる識別子が含まれない。検証は次の出力を根拠にする。
   `grep -rniE '<移植先の組織名>|<移植先のリポジトリ名>|<移植先のホスト名>' task/0044-second-project-port/` が 0 件（実行時は実際の名前を渡す。**この spec には書かない**）。
8. このリポジトリ側の `tools/*.mjs`・`CLAUDE.md`・`.claude/skills/loop-port/SKILL.md` に差分が無い。`git diff --name-only main...HEAD` の出力が `task/0044-second-project-port/` 配下だけである。
