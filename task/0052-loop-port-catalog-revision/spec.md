# `loop-port` カタログの改訂（実地で見つかった 5 項目の追加）

`.claude/skills/loop-port/SKILL.md` の変更箇所カタログ（2 章、現在 13 節）に、2 件目・3 件目の移植で実地に見つかった 5 項目を節として足し、4 章「アンチパターン」に対応する 1 項目を足す。

## 種別

改善

## 対象

- 場所: `.claude/skills/loop-port/SKILL.md`（2 章「変更箇所カタログ」と 4 章「アンチパターン」）
- 公開面: なし。エージェントが読む手引き（Skill 本文）であり、コードの API や UI は持たない

凍結対象ではない。`tools/check-protected-paths.mjs` の保護対象に `.claude/` は入っていない。したがって `allow-protected-change` ラベルは不要であり、凍結改訂の手続きも適用しない。`tools/`・`CLAUDE.md`・`.claude/settings.json` は触らない。

## 背景

`loop-port` カタログは 1 件目の移植の実測（2026-08-27）を基に書かれ、13 節（2.1〜2.13）で止まっている。その後の移植で、カタログに無いために踏んだ項目が 5 件ある。

**4 件は記録済み。** `task/archive/0044-second-project-port/notes/port-log.md`（以下「記録」）の 5 節「`loop-port` スキルへ」が、カタログへの追加を申し送っている。記録自身は spec の「範囲外」によりスキルを改訂していない。記録との対応は次のとおり。

| # | 項目 | 記録の該当節 |
|---|---|---|
| 1 | 定数を差し替えても利用者向け文言は追随しない | 2.7 の表「新規」1 行目と、直下の小節「新規項目『定数を差し替えても文言は追随しない』」（実測で 5 回踏んだ）。3 節の行 15・24 |
| 2 | 台帳が同じリポジトリで git 追跡されていること（移植の前提条件） | 2.6 (a)。5 節「0042 へ」6 |
| 3 | 移植先に既存のループがある場合は、置き換えではなく対応づけ | 2.6 (c)。2.5「書き換えた記述」行 3・6、「移植して分かったこと」。5 節「0043 へ」1 |
| 4 | Stop hook の終了コード（止めるのは 2。1 は非ブロッキング） | 4 節 (c)。3 節の行 21。「移植元への申し送り」の引用ブロック |

**5 件目は 2026-09-02 の 3 件目の移植で判明し、この spec 以外に記録が無い。** 内容は次のとおりで、実装はこの記述を出典とする。

> 移植先の既存ワークフローを**撤去**する場合、項目 3「置き換えではなく対応づけ」の助言は当てはまらない。撤去すると、記録が「未解決」としていた 2 件（台帳ライフサイクルの衝突 2.6 (d)、別名 spec の衝突 2.6 (e)）は解消する。代わりに**導入 PR 自身がゲートに落ちる**という別の問題が現れ、これは docs PR と実装 PR の 2 本に分けることで解ける。
>
> - 進捗結合の検査は「base に既にある progress の内容を書き足した更新」だけを数えるので、spec + progress を実装と同じ PR で作ると必ず落ちる。これはブートストラップの例外ではなく、移植先での最初の適用例である
> - 凍結ガードは、移植先に既にある保護対象（hook の配線・CI ワークフロー・既存テスト）を変更するぶんを検知するので、実装 PR には `allow-protected-change` が要る。ラベルは移植先のリポジトリに存在しないことがある（3 件目の移植では作成が必要だった）
> - 実測の順序: docs PR（spec + progress + テンプレート）を先に main へ入れる → 実装 PR の base をそれにする → マージ後に base を main へ切り替える

移植元（このリポジトリ）の Stop hook も、項目 4 の穴を今も持つ。`.claude/settings.json` の Stop hook は `… && npm run ci 1>&2 && … check-actions.mjs` の形で、`npm run ci` が落ちると exit 1 で終わる一方、`tools/check-actions.mjs` は止めるときに exit 2 を使う（`:198`、`:344`）。この spec はカタログにその事実を書くだけで、hook 自体は直さない（「範囲外」）。

## 仕様

変更後の `SKILL.md` は次を満たす。

### 2 章に 5 節を足す

既存の 2.1〜2.13 に続けて、次の 5 節をこの順・この見出し文字列で足す。番号は既存に連続させ、既存の節番号は変えない。

| 節 | 見出し（`### ` の後ろの文字列） | 出典 |
|---|---|---|
| 2.14 | `2.14 利用者向け文言の追随` | 記録 2.7「新規項目」、3 節 行 15・24 |
| 2.15 | `2.15 台帳の git 追跡（移植の前提条件）` | 記録 2.6 (a) |
| 2.16 | `2.16 移植先に既存のループがあるとき` | 記録 2.6 (c) |
| 2.17 | `2.17 Stop hook の終了コード` | 記録 4 節 (c) |
| 2.18 | `2.18 既存ワークフローを撤去するとき（導入 PR の分割）` | この spec「背景」 |

各節は、既存の節と同じ書式で書く。

- 「場所 / 現在の値」の表（列見出しは既存と同じ `| 場所 | 現在の値 |`。効果の列を足すのは既存 2.2 と同じく任意）
- 続けて `**方針。**` で始まる段落
- 節の末尾に出典の行を 1 行置く。行頭から `出典: <パス> <節番号>` の形で、パスをバッククォートで囲まない（grep で数えるため）。パスは 2.14〜2.17 が `task/archive/0044-second-project-port/notes/port-log.md`、2.18 が `task/0052-loop-port-catalog-revision/spec.md`（アーカイブ後は `task/archive/` 配下に移る旨を括弧で添えてよい）。例: `出典: task/archive/0044-second-project-port/notes/port-log.md 2.6 (a)`

各節の「場所 / 現在の値」と「方針」に必ず含める内容は次のとおり。文面は実装者に任せるが、下の命題を欠かさない。

**2.14 利用者向け文言の追随**

- 場所: `tools/check-progress-coupling.mjs`・`tools/guard-worktree.mjs` の利用者向け文字列リテラル（`console.error` / `console.log` の実引数）。現在の値: `progress.md`・`task/<id>-<slug>/progress.md`・`node tools/start-task.mjs` などの語彙が定数ではなく文字列に直書きされている
- 方針: 定数（`IMPLEMENTATION_DIRS`・`TASK_DIR`・`PROGRESS_FILE` 相当）を差し替えても文言は追随しない。エラー経路だけでなく**成功時の文言**と**めったに通らない分岐**（`foreign` 経路、ガードが案内する開始コマンド）も見る。記録では書いた後も含めて 5 回踏んでおり、人手で潰す限り漏れるので、利用者向け文字列に対する移植元語彙（`progress.md`・`task/`・`npm run ci`・`tools/`）の走査を移植の受け入れ確認に入れる。コメントは対象外

**2.15 台帳の git 追跡（移植の前提条件）**

- 場所: 移植先の `.gitignore`。現在の値（移植元）: `task/` は追跡されている
- 方針: 凍結ガードも進捗結合の検査も git の差分を見るので、台帳が追跡されていなければどちらのゲートも原理的に成立しない。これはマニフェストの項目ではなく**移植可否の前提条件**である。台帳を追跡に切り替えるのは技術的修正ではなく方針変更（台帳に顧客固有情報が載る）なので、移植者が黙って `.gitignore` を変えず、人間の判断を仰ぐ。満たせない移植先ではゲート層を移植できない

**2.16 移植先に既存のループがあるとき**

- 場所: `CLAUDE.md` の開発ループ 7 工程、`tools/start-task.mjs` の Plan 入口、2.12 の不変の原則。現在の値: カタログは移植先に `CLAUDE.md` やフェーズ運用が無い前提で書かれている
- 方針: 既存のフェーズ・クオリティゲート・レビュアーがあるなら**置き換えず対応づける**。「既にあるものを見つけて、無いものだけ足す」。原則が同じでも置き場は既存節の中（記録の「Critical ゼロ」は既存節への 1 行追記が正解だった）。Core は「台帳の層」と「ゲートの層」に分けて考え、既にある層は移植しない。2.18 が例外（撤去する場合）であることを明記する

**2.17 Stop hook の終了コード**

- 場所: `.claude/settings.json` の Stop hook、`tools/check-actions.mjs:198,344`。現在の値: hook は `… && npm run ci 1>&2 && …` の形で検証失敗時に exit 1、`check-actions.mjs` は止めるときに exit 2
- 方針: セッションを止めるのは **exit 2** だけであり、exit 1 は非ブロッキング（表示はされるが止まらない）。移植先では検証失敗の経路を exit 2 にする（記録の移植先の形: `{ <検証コマンド> 1>&2 || exit 2; }`）。hook の登録（`settings.json` 相当）が無ければ exit 2 を返しても何も起きないので、登録まで含めて 1 セットとする。移植元自身にこの穴が残っていることを明記する

**2.18 既存ワークフローを撤去するとき（導入 PR の分割）**

- 場所: `tools/check-progress-coupling.mjs`（base に既にある progress の更新だけを数える）、`tools/check-protected-paths.mjs`（既存の保護対象の変更を検知する）、`guard.yml` / `ci.yml` のラベル。現在の値: 2.16 は既存ループの対応づけを説く。コミットとマージの表（2.12 不変）は spec/progress を docs PR で先に入れることを前提にする
- 方針: 「背景」の引用ブロックの内容をすべて含める。すなわち、(1) 撤去なら 2.16 の対応づけは当てはまらず、記録 2.6 (d)(e) の未解決 2 件は解消する、(2) 代わりに導入 PR 自身がゲートに落ちる、(3) 進捗結合は新規作成を数えないので spec + progress を実装と同じ PR に入れると必ず落ちる（ブートストラップの例外ではなく最初の適用例）、(4) 実装 PR は既存の保護対象を変えるので `allow-protected-change` が要り、ラベルは移植先に存在しないことがあるので作る、(5) 順序は docs PR（spec + progress + テンプレート）→ 実装 PR の base をそれにする → マージ後に base を main へ

### 4 章「アンチパターン」に 1 項目を足す

既存の箇条書きの末尾に、`**導入 PR を 1 本にまとめる。**` で始まる 1 項目を足す。内容は 2.18 の要約（spec + progress + 実装を 1 本の PR にすると進捗結合で必ず落ちる。docs PR を先に入れる）とし、2.18 を参照する。

### 変更は追加のみ

既存の行を削除・書き換えない。frontmatter（`name` / `description`）も変えない。差分は追加行だけになる。

## 範囲外

- `tools/`・`CLAUDE.md`・`.claude/settings.json`・`.github/workflows/` の変更。とくに Stop hook の終了コードを exit 2 に直すこと（別作業。backlog 候補）
- 利用者向け文言の禁止語走査の機械化（記録 5 節「0043 へ」4・6-C）
- 既存 2.1〜2.13、0 章・1 章・3 章の本文改訂。1 章の実測表を 2 件目の移植で更新すること
- `task/archive/0044-second-project-port/` の変更（凍結対象。読むだけ）
- 3 件目の移植の記録を別ファイルとして残すこと（この spec の「背景」が出典になる）

## 失敗時

- `guard.yml` の `protected-paths` が違反を報告する: この作業の差分が `.claude/skills/loop-port/SKILL.md` 以外の凍結対象に及んでいる。差分を戻す。ラベルで通さない
- `git diff` に削除行がある: 既存の本文を書き換えている。追加だけに戻す

## 完了条件

次をすべて満たしたとき、この仕様は完了とする。検証はこれらの条件に対して行い、テスト実行結果などのコマンド出力を根拠にする。

1. 「対象」が仕様どおりに公開または修正されている。
2. 「例」がすべて、テストまたは再現手順で同じ結果になる。
3. 「失敗時」に書いた入力・操作で、仕様どおり失敗する。該当がなければこの項は「なし」。
4. 「範囲外」を実装していない。
5. 2.14〜2.18 の 5 節が「仕様」の表の見出し文字列・順番で存在し、各節が「場所 / 現在の値」の表・`**方針。**` 段落・`出典:` 行の 3 要素を持つ（「例」の 1〜7 行目の出力を根拠にする）。
